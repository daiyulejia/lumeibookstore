## 二、主线：可搜源池只会单向缩水，缩到 0 之后回不来

既然没有线上流量，就顺着「本地库里那个 0」往下查。`/api/registry` 报
`sites_searchable = 0`（334 个站、211 个健康），而**自有来源就是靠
`searchable_sites()` 扇出的**（`sources/registry_source.py` 第一行就取它）——
也就是说这条资产对每次搜索的贡献是零，搜索只剩 7 个内置源在撑。

全库只有 **4 个站**还有 `search_tpl`，而它们**一个都不可搜**。
四个的判据失效点完全一致：

| 站 | ok | fail_down | 2×ok+1 | 判为不健康 |
|---|---|---|---|---|
| www.tadu.com | 60 | 121 | **121** | 是 |
| www.384g.com | 386 | 773 | **773** | 是 |
| www.biqugela.cc | 6 | 13 | **13** | 是 |
| www.ldxs1.net | 7 | 15 | **15** | 是 |

分子分母都恰好落在 `down == 2*ok + 1` 上，四个数量级完全不同（6 / 7 / 60 / 386）。
这不是巧合，是**「越线即冻结」的指纹**：

```
down > 2*ok  →  is_healthy 判否
             →  searchable_sites() 不再扇出它
             →  discovery._verify 也跳过它
             →  永远拿不到下一次成功 → ok 不再增长
             →  计数就地冻结（冻结点必然是最小的越线整数 2*ok+1）
```

### 病根有两层，缺一层都解释不了它为什么能一直烂下去

**① 我方限流被记成「站点挂了」**

`utils.fetch_text` 在同域限流冷却期内**一个请求都不发**（这是我们自己的保护），
抛 `errors.LocalCooldown`。而下面这两行原本在 **6 个地方**各写了一遍：

```python
slow = classify_fetch_error(e) == "slow"
why  = registry.FAIL_SLOW if slow else registry.FAIL_DOWN
```

`LocalCooldown` 是 `RuntimeError`、不是 httpx 超时 → 归到 `other` → 不是 slow
→ **记 `FAIL_DOWN`「站点网络层失败」**。实测（本机）：

```
LocalCooldown(37.5,'x') → classify_fetch_error → 'other' → FAIL_DOWN
```

6 个入口：`discovery._verify`、`discovery._check_book`（坏源排查）、
`registry_source._search_one`、`registry_source.fetch_chapter`、
`web.fetch_chapter`、`web.probe`。

11-16 给引擎装了「自限流不是源故障」（`source.skip`），**只改了 engine 和 ranks**。
病根是当时的清单：查的是 `note_fail`（熔断器），而这一批入口的共同点是
`classify_fetch_error` —— 换个关键词 grep 就能看见 6 处，当时没查。

冷却在日志里天天出现（11-13/15/16 三天）：
`xbqg5200`×9、`wikisource`×5、`wyshu`×4、`luoxiaks`×1。
前三个是内置源（走引擎，已修），**`luoxiaks` 是自有来源的站** ——
它一进冷却，同一轮里对它的核实/取正文就会被记成"站挂了"。

**② 越过死亡线没有回头路（放大器）**

`is_healthy` 只有死亡线、没有复活路径（见上面的冻结指纹）。
即使 ① 停止误记，已经误杀的站也回不来 —— 池子只会单向缩水。
