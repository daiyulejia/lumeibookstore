# 2026-11-15 复盘：线上不可达第 3 天；抓到「源自述 6s、调用方只等 1.5s」的整类浪费

## 0. 一句话

**线上实例从 11-13 00:17 之后就一直不可达（今天用 6 个境外节点复核），所以这一轮没有
任何真实用户流量可复盘。** 本地把「源自己声明的预算」这一整类问题挖到头：
`wyshu` 是 100% 无效负载（永远冷索引 → 0 产出），`wikisource` 声明 6s 实测 7.33s。
两个都修了、都反证了；**但没法上线**（部署目标不在线）。

## 1. 今天为什么不能写「没有新案例」

往年「零搜索」有两种，这两种在日志里长得一样，处置完全相反：

| 情形 | 判据 | 该写什么 |
|---|---|---|
| 服务在线、没人搜 | `search.start` = 0，但 `/api/health` 通 | **没有新案例**（如实记） |
| **服务不在线** | 端口/ICMP 全不通 | **没有数据，不能判** |

今天属于第二种，所以「没有新案例」这句话**今天不成立**（11-13 已把这条口径写进规则：
自检探针不算真实流量；今天再加一条：**拉不到日志 ≠ 没人搜**）。

证据（2026-11-15 01:2x 实测）：

| 探测 | 结果 |
|---|---|
| 本机 TCP 22 / 80 / 443 / 8000 | 四个全 `TimeoutError`（6.0s）——**不是 refused** |
| 本机 ICMP | 3 发 3 丢（100%） |
| check-host.net（de / es / il / ir×2 / ru 六节点）TCP 8000 | 六个全 `Connection timed out` |

产品崩了会给 `refused`（有回包）；连拒绝都没有、六个境外节点一致超时 → **主机级不可达**，
不是我们的网络、也不是进程挂了。这台实例的最后已知可用时刻是 11-13 00:17:54
（`6adaf5a` 部署重启），之后到今天三天。**无控制台凭证，不猜是哪一种**
（停机 / 欠费 / 安全组 / IP 变更），只能报给用户。

本地补充：`logs/app.log` 最后一条是 11-13 09:57；11-14 02:17 守护脚本打印
「服务退出（code=1073807364）→ 3s 后重启」之后**再没有任何写入**，今天 01:20 才重新起来。
所以本地 11-14 也是零搜索。

## 2. 主线 A：`wyshu` 是 100% 无效负载（不是慢，是**永远交不出东西**）

### 2.1 现场（今天本地真机，一行日志定案）

```
01:21:20 搜索收手：已返回 2/7 个源（29%）…耗时 1.5s，放弃 5 个…（…, wyshu）
01:21:25 wyshu: 索引构建到点收手：已抓 6/8 个分类、594 本（预算 6s，本轮不写缓存）
01:21:28 search.done … 未回=5(…, wyshu)
```

引擎 1.5s 就把它扔了，它 6 秒后抓到的 **594 本被整批作废**。

### 2.2 三层根因（每层都单独足以让它白干）

1. **冷索引永远冷**：8 个分类页串行实测 **4.25s**（并行 3.07s —— 站点会限速，
   「并行就快」在这里不成立，值得记一笔），而收手在 1.5s → 每次都被截断 →
   `complete=False` 不落盘（10-24 定的规矩，防"残缺索引固化 24h"）→
   下一轮又是冷的 → **它 100% 的时间都在重建一份永远用不上的索引**。
2. **声明 6s，实际跑 10.2s**：直连实测 12 本真书，《我的阿勒泰》**10230ms**。
   预算只在**请求之间**判定，一次慢读就突破 70%（与 11-09 `taiminc` 7.3s 同源）。
3. **拼音兜底是纯消耗**：12 本里 10 本走到它，**0 命中**，每本烧 2.7~4.0s。

### 2.3 控制实验（12 本真实书名，直连这个源、不经引擎）

| 书名 | 改前 | 改后 |
|---|---|---|
| 三体 | 5042ms / 1 条（建索引） | 15ms / 1 条 |
| 鬼吹灯 | 0ms / 13 条 | 0ms / 13 条 |
| 诡秘之主 | 1505ms / 0 条 | 1474ms / 0 条 |
| 兄弟 | 2711ms / 0 条 | 1574ms / 0 条 |
| 我的阿勒泰 | **10230ms** / 0 条 | 计入 1.5s 预算内 |
| 其余 7 本 | 0~4.7s / 0 条 | 同上 |

结论：**命中 2/12，且这 2 本别的源也给了**（同一轮 `xbqg5200` 1.12s 就给了《三体（全集）》）。
所以它的边际贡献 = 0 —— 这正是 11-13 欠账「wyshu 是否也声明 `budget_s`」的答案：
**不声明**。让引擎为它多等 3.5s 是纯亏。

### 2.4 修法（三件事，一行引擎都没改）

1. **搜索只读缓存，冷的踢后台**（`_cached_index()` + `_kick_build()`）：
   冷的时候本轮 0ms 返回 []，后台线程用 6s 预算慢慢建、建完落盘。
   → 实测：冷 0ms → 后台 794 本落盘 → **下一轮 0ms 且真有产出**（鬼吹灯 13 条）。
   这是我们**主动不要**，而不是被引擎扔掉 —— 判别这两者，日志里是
   「wyshu 索引冷：本轮不参与（已踢后台构建，不占搜索墙钟）」。
2. **拼音兜底独立预算 `PINYIN_BUDGET=1.5`**（原来共用一个 6s）：它每次搜索都跑、
   12/12 空手，凭什么按建索引的额度烧钱。
3. **每次请求夹墙钟 `min(剩余, 1.0)`**（`fast_mode(retries=0, …)`）：把「声明了预算」
   变成「真的有上限」。取 1.0 而不是 2.0 是因为 httpx 的 timeout 是**分操作**的
   （11-09 那一课），给 1.5s 实测能跑出 2.09s。
4. **后台构建单飞闸门**（`_BUILD_LOCK` + `running` + 120s 重试间隔）：别每轮搜索各起一份、
   同时压 8 个分类页。

## 3. 主线 B（同一母题的第二处）：`wikisource` 声明 6s，实测 7.33s

对照实验（3 本真书）：**3/3 都是 0 条，各 7.2~7.3s**。

根因：请求超时**早就**夹了剩余预算（`left = max(0.5, deadline - now)`），
但**两次退避睡眠是无条件的**，睡完也不再看表 —— `1.0*(i+1)+0.5*i*i`（最坏 2.5s）
就是那多出来的 1.2~1.3s。

修法：抽 `_backoff(seconds, deadline)` 统一两处退避 —— 剩余不足就**一秒都不睡**，
否则取 `min(退避, 剩余)`。判据看「睡多久」，不看总耗时。

## 4. 举一反三

**同一母题（源自述预算 ≠ 调用方肯等的时间）会不会在别的源上复发？**

| 源 | 自述预算 | 会不会中招 | 处置 |
|---|---|---|---|
| `wyshu` | 6.0s / 拼音无独立预算 | **已中**（今天修） | 只读缓存 + 后台建 + 独立预算 |
| `wikisource` | 6.0s | **已中**（退避不认表，今天修） | `_backoff` |
| `registry`（30 个自有站） | `budget_s=5.0` | 不中（11-09 已声明让路，⓿ 组钉住 5.0 < 6.0） | — |
| 其余内置源 | 无自述预算 | 不适用 | — |

**预计还影响：0 个未修**（`grep CACHE_TTL\|_load_index app/sources/*.py` 只有 wyshu 一个自建索引源）。

**但今天挖出一个没人管的洞（未修，留欠账）**：引擎收手条件 ①
（`确切>0 且 raw>=12`）**不看任何源声明的预算**，1.5s 就能收手 ——
今天本地那次就是 ① 触发的（`原始 12 条/确切 1 条/耗时 1.5s`），
wyshu 与（线上）registry 都被它越过。11-09 的「让路」只装在 ②③。
为什么不今天改：改它要动 `test_search_recall` 的耗时基线，而**线上不可达、
没有真实流量验证代价**（改完每个搜索都会慢 2~4s），盲改风险大于收益。

**判据为什么没抓到这两处？** 不是清单漏项，是**压根没有判据**：
`未回=wyshu` 只回答"它没回来"，不回答"我们肯等几秒 vs 它要几秒"；
`SEARCH_BUDGET=6.0` 只是一句自述，没有任何东西验证"真花了多少"。
今天补的判据全部钉**结构事实**（同步路径有没有抓取 / 后台有没有起来 / 传给 httpx 的超时是多少 /
退避睡了多久），**不用耗时阈值**（会随机器负载漂）。

# 第二部分（09:20 第二轮）：榜单定时刷新「撞预算」在唯一真实调用路径上沉默收手

> 同一个日期跑了两轮（01:20 与 09:20）。第一部分的「实例不可达」结论仍然成立，
> 下面的编号是这一轮自己的。

## 0. 一句话

线上实例**第 4 天不可达**（09:2x 复测 22 / 8000 仍 `TimeoutError`），所以依然没有真实
搜索流量可复盘；这一轮的主线来自**本地实例的日志**——榜单定时刷新一晚三次
「撞预算收手」，而它报的是「成功 6 / 失败 0」：**少更新了一类榜单，日志里一个字都没有**。

## 1. 为什么今天仍然不能写「没有新案例」

| 探测（2026-11-15 01:2x 与 09:2x 各一次） | 结果 |
|---|---|
| 本机 TCP 22 / 80 / 443 / 8000 | 四个全 `TimeoutError`（**不是 refused**） |
| 本机 ICMP | 3 发 3 丢 |
| check-host.net 德/西/以/伊×2/俄 六节点 TCP 8000 | 六个全 `Connection timed out` |

主机级不可达，不是进程挂了、也不是我们的网络。拉不到线上日志 ⇒ **没有数据可判**，
不是「没有新案例」。**未部署**（见 §7）。

本地 `logs/app.log` 今天只有自动化自己的探针；但 `logs/server-2026-11-15.log`
（本地实例，01:21 起）里有**真实的产品行为**可查 —— 这一轮就是从这里挖的。

## 2. 主线：`pending` 在唯一的真实调用路径上被丢掉了

### 2.1 现场（本地实例日志，一晚三次）

```
  [ranks] 刷新超预算（25s），先收手：已完成 6/7
  [sched] 榜单刷新完成：成功 6 / 失败 0，耗时 25.01s
  [ranks] 刷新超预算（25s），先收手：已完成 6/7
  [sched] 榜单刷新完成：成功 6 / 失败 0，耗时 25.02s
  [ranks] 刷新超预算（25s），先收手：已完成 5/7
  [sched] 榜单刷新完成：成功 5 / 失败 0，耗时 25.01s
```

前后没有一行 `[ranks] xxx 抓取失败` —— 那个慢源**既不报错，也没有名字**。
而「成功 6 / 失败 0」读起来像是一句好消息：**没人知道少了一类**。

### 2.2 三条根因（同一处）

1. **闸门只装在 HTTP 入口上**。`/api/ranks/refresh` 那条路一直有埋点
   （`没跑完=N 类目=…`，2026-10-22 就加了）；但**定时任务是直接调
   `ranks.refresh()` 的**，根本不经过那个入口 → 唯一每 30 分钟跑一次的路径
   把 `pending` / `pending_kinds` 全丢了。（与 11-11「闸门装在一个入口上
   就等于没装」是同一母题，只是这次漏的是 sched 这一侧。）
2. **`sched.status()` 里没有 pending 字段** → `/api/ranks/status`
   （运维唯一的口子）也看不出来。
3. **`last_error` 用 `ok+failed` 判「全灭」**，被预算放弃的类既不算成功也不算失败
   → 「6 成功 1 放弃」和「7 类全部被放弃」都报 `last_error` 空。
   最极端的那个组合（全被放弃）恰恰是**最像成功**的那一种。

### 2.3 顺带查出的结构性缺陷：**一次抓取的默认超时 = 整轮预算**

`fetch_text` 的默认超时是 25s（`httpx.Timeout(25.0, connect=12.0)`），
而 `RANKS_REFRESH_BUDGET` 也是 25s —— 于是**一个源慢一点，就必然吃掉整轮预算**，
代价是"某一类这一轮不更新"。今天逐源逐类实测（13 个「来源×类目」组合）：

| 来源 | 类目 | 耗时 | 条数 |
|---|---|---|---|
| 384g | lastupdate | **2.39s**（最慢） | 24 |
| 384g | 其余 4 类 | 0.39~0.65s | 24 |
| xbiquge | allvisit / week / last / lastpost | 0.53~0.98s | 20~30 |
| luoxiaks | 5 类 | 0.22~0.71s | 30 |
| hodei（`once`，一轮只抓一次） | 5 类 | 0.55~1.18s | 15 |

正常一轮 7 类 **2.5~3.6s**。能突然跑到 25s，说明有源**间歇性卡住**
（不是稳定慢），而卡住的代价全是"少一类"，且不可见。

**实测墙钟有没有牙**（把源指向一个 SYN 被丢的端口 `https://www.baidu.com:81/`）：
`fast_mode(retries=1, timeout=6.0)` 下 **12.89s** 放弃（= 6 + 0.8 退避 + 6，
正好压在 `6s×2+退避` 的上限上）；旧行为是 25s 一次、最多 4 次尝试，
被调用方 25s 掐断时那一类已经废了。

### 4.2 这条判据为什么没抓到它？——三层，最外层最致命

1. **判据压根没被登记**：`tools/test_sched.py` 有 312 行、断言也不差，

### 4.3 影响面（诚实估计）

被放弃的类**保留上一轮缓存**（`_CACHE` 不覆盖），所以用户看到的是
「某一类榜单最多滞后一轮（约 1 小时）」，不是空白页。严重性不高，
但正因为"不空白、不报错"，它会长期隐形 —— 极端情况下某类榜单可以是半个月前的
而没有任何一处说得出来。
