## 四、主线：一个装饰字符把服务打死在监听之前

### 4.1 现场（不是猜的，日志里躺着 542 份同一条栈）

```
2026-11-13 00:00:44 启动
[00:00:47] 服务退出（code=1，存活 2s）
[00:00:47] 60s 后重启…
…
2026-11-13 09:25:14 启动
[09:25:14] 服务退出（code=1，存活 2s）
```

`logs/server-2026-11-13.log` = 557KB，`UnicodeEncodeError` **542 次**，
`grep -c 启动` 也是 542。同一份日志在 11-12 已经有过 **108 次**。

### 4.2 根因链（四步，缺一不崩）

1. `tools/serve.py`（"让服务长期挂着"的官方姿势）用管道接子进程 stdout；
2. Windows 上管道的默认编码是 **cp936(GBK)**；
3. `run.py` 的启动横幅里有个 `⇄`（U+21C4，借解释器提示那行）——GBK 里**没有这个字**；
4. `print()` 直接抛 `UnicodeEncodeError`，异常从 `_borrow_exe()` 冒到 `main()` 外，
   **进程在 `uvicorn.run()` 之前就退了** → 守护脚本 60 秒后再拉一次 → 无限循环。

用户侧看到的是「窗口一直滚 traceback，网页打不开」，而栈里那行还是乱码,
看不出是哪个字符。

### 4.3 修法（`run.py`）

- 新增 `_harden_stdio()`：**只放宽 `errors`，不换 `encoding`**。
  换 encoding 会把中文（地址、令牌、防火墙提示）变成乱码，而那些字正是用户要看的。
- **编码得了的流一个字节都不动** —— 全量改成 `replace` 会让整个程序的编码错误
  静默退化成一个 `?`，以后真出编码 bug 连抛都不抛。
  判据是「这个流能不能表示 `_STARTUP_GLYPHS`（⇄ → ⚠ ✓ ·）」。
- `main()` 第一句就调它（后面横幅/防火墙提示/借解释器提示都带这些符号）。
- 顺带把借解释器那段文案抽成 `_borrow_hint()`：**它原来只藏在那条要靠防火墙
  检测才走得到的分支后半段，测试打不出来**，所以才会"没人发现"。

### 4.4 判据 + 反证

新增 `tools/test_startup_encoding.py`（13 项，已登记 `ship.py` 的 `STATIC_SUITES`）：

| 组 | 验什么 |
|---|---|
| A | `PYTHONIOENCODING=gbk` 真跑：加固后 rc=0；**不加固时 rc≠0 且死因是 UnicodeEncodeError**（这条同时是永久反证 —— 证明洞真实存在） |
| B | 只退化不能编码的字符；中文**原样落盘**不许变 `?` 串 |
| C | 反向：utf-8 流 `errors` 必须还是 `strict`（不吞真错误）；非 TextIOWrapper 的流不许被改、更不许抛 |
| D | 端到端：GBK 真流 + 真 `main()`，走 `--host 0.0.0.0` 那条路，断言**横幅和带 ⇄ 的那行都真的打出来了** |

反证 `tools/mutate.py 启动编码` 4 条 → **4/4 全抓、源码逐字节还原**：

```
✓ main() 不做输出加固            → D 组红（UnicodeEncodeError）
✓ 编码不了也照旧 strict          → A/B 红
✓ 探测符号改成编码得了的          → A/B 红
✓ 编码得了也强行 replace          → C 组红（errors='replace'）
```

（第一版 D 组**没抓住**第一条：它只走到横幅，根本不经过带 `⇄` 那行 ——
所以才把文案抽成 `_borrow_hint()` 重做。这与 10-25「埋点要埋在人看得见的那批
对象上」是同一个教训：**测"启动成功"不等于测到了崩溃点**。）

### 4.5 举一反三

**（1）同类影响面：还有 12 个脚本、共 102 处 `print` 带 GBK 编不了的符号**

`tools/{adapt_pool, build_assets, firewall, gzip_static, logs, mutate, pack,
restart_check, service, ship, sync_cloud}.py` 都在打 `✓ ✗ ⚠ ✅ ❌`。
但它们平时打在**控制台**（走 `WriteConsoleW`，不经过编码），只有被重定向/管道
接住时才会中招；用户路径上常驻、且被管道接住的**只有 `run.py` 一个，已修**。
→ 结论：不追加修改，但"新写的常驻脚本要不要加固 stdio"应成为检查项。

**（2）这条判据为什么一直没抓到它？—— 清单漏项 + 压根没埋点**

- 真机套件起服务用的是 `LocalServer`，参数固定 `--no-check`
  → **恰好绕过了唯一会崩的分支**（`_borrow_exe`）；而且 `stdout=DEVNULL`
  → 就算崩了也只报"本地服务没起来"，**没有一个字的原因**。
  这两条叠起来，等于这个分支从来没被任何自动化走过。
- 补的是 A~D 四组静态判据（不依赖服务、不依赖浏览器）。
- **顺带把诊断洞也补了**：`LocalServer` 原来把子进程 stderr 指向 `DEVNULL`，
  起不来时只报"本地服务没起来（端口 N）"—— 原因（缺依赖/端口占用/编码崩/配置错）
  全被扔掉。现在 stderr 落到临时文件，失败时把尾巴贴进报错里。
  两条路径都验过：
  - 正常：`/api/health` 返回 ok、`server-stderr.log` 生成；
  - 失败（先把端口占住）：报错里直接带上
    `ERROR: [Errno 10048] error while attempting to bind on address …`，
    中文也按 gbk 回退解出来了。
  这和 `run_suite` 里那条「✗ 落在倒数 30 行外、原因看不见」是同一个教训 ——
  那次之后 `run_suite` 改了，`LocalServer` 漏掉了。
