## 三、主线根因：长书只下到前 100 章

把目录完整性这件事单独捞出来看（`webfetch` 的 `toc_completeness` 判据 A/B/C），
今日日志里 5 个不同的书页都在喊同一句话：

```
目录可能不完整（只有第 1–1623 章中的 105 章）：https://www.xbiquge.info/0/143/
目录可能不完整（只有第 1–1004 章中的 106 章）：https://www.384g.com/html/204/204269/
目录可能不完整（只有第 1–2166 章中的 104 章）：https://www.384g.com/html/41/41562/
目录可能不完整（只有第 1–2166 章中的  26 章）：https://www.axxsw.net/index/21/21894/
目录可能不完整（只有第 1–844 章中的 105 章）：http://www.yuanzun888.com/book/68478/
```

一本 2166 章的书，我们交出去 104 章 —— 用户看到的是"下载了，但只有一小段"。
而 `search.done` 那边一切正常：`候选=1 成书=1 可读=1`，**这条缺陷在账本里没有任何字段**。
所以它躺了很久没人发现。

### 三层原因，缺一层都复现不出来

**① 分页器一个都不认。** `_next_page_url()` 原来只认一件事：
`url_template(new) == url_template(cur)` 且路径里的数字**连续递增**。
而长书目录的分页是三种主流形状，全都不符合"连续递增"：

| 形状 | 例子 | 为什么原判据不认 |
|---|---|---|
| 杰奇 CMS | `/html/1/9001_2/` | 末段是 `9001_2` 复合串，不是纯数字 |
| 数字槽位式 | `/book/57620/2/` | 末段 `2` 是**页码**，和书本 id 不是同一个槽 |
| 下划线文件式 | `/0/98/index_2.html` | 页码在文件名里，且首段 `0` 会干扰"递增" |

→ 认不出"下一页"，目录就停在第一页的 ~100 条。

**② 认出来了也只看 5 页。** `_merge_paged()` 固定 `budget=5`，而 2166 章要 21 页；
更要紧的是收尾逻辑：只有"撞页数上限"才置 `pending=True`，
**墙钟到点、模板不符这两种情况都是静默退出** —— 拼了一半也当完整交上去。

**③ 核实与下载共用同一份目录。** 探测/抽样（`probe`/`sample`）和下载（`get_chapters`）
原来都走 `get_chapters()`，也就是**都按整本预算去跟分页**。
一本 21 页的书，光是"看看这本书能不能下"就要花 20+ 秒，搜索预算直接被打穿；
反过来为了省时间又把页数压到 3 页 —— 核实和下载的需求是相反的，却共用一根旋钮。

### 改了什么

| 文件 | 改动 |
|---|---|
| `app/webfetch.py` | `_next_page_url()` 加第二种形状兜底：`_paged_siblings()` 收集页面上**与本页同前缀、末段为 1~3 位纯数字或 `index_N`/`xxx_N` 的兄弟链接**，取最小那个当下一页（`_PAGE_NO_RE` 判页号）。新增四档预算常量 `TOC_MERGE_PAGES/WALL/FULL_PAGES/FULL_WALL`（核实 3 页/3s、下载 40 页/25s）。`_merge_paged()` 加**墙钟预算**并按上一页耗时预估提前停（避免 2s/页的站把 3s 墙钟跑成 7s），收尾改**无条件**检查 `more = _next_page_url(...)`：撞页数、撞墙钟、模板不符**三种都置 `pending=True`**，不再静默 |
| | 新增 `_split_toc_sections()`：有的站把"最新九章"和"章节目录"并排写在一页（如 384g），只取整页会把最新章节重复算进目录。做法是从**每一处**「章节目录/章节列表/全部章节/正文目录」标题切片，取**条数最少但仍≥半页**的那份（切得最干净），切得太碎不算数；并加 `len(latest)*2 > len(best)` 兜底防误切。切出来的"最新块"拼到目录**末尾** |
| | `_order_chapters` 保持"每一条都认得出章号才排"的原判据 —— 实测 384g 的章号本身就乱（第五十章出现 5 次分属 5 段连载），强排会交叉错位，这一版**回退**了改法只补注释 |
| `app/discovery.py` | `page_of(url, force, full)`：`full=True` 时**不吃"残目录"缓存**（缓存里 `toc_pending=True` 的那份不返回） |
| `app/sources/base.py` | 新增 `read_toc(result, full=False)`（默认退化为 `get_chapters`）；`probe()`、`sample()` 都改走 `read_toc()` —— **探测不再跟分页到底** |
| `app/sources/registry_source.py`、`web.py` | 同构拆成 `read_toc(full=False)` + `get_chapters = read_toc(full=True)`；`sample()` 用快的那条 |
| `app/sources/configured.py` | `_repair_toc(chapters, html, base, fast=)`：不再"够多且不 partial 就 return"，**总是**先切"最新块"再跟分页，最后把 tail 拼到末尾；`_load_detail(fast=)`；新增 `read_toc(full=False)` 走 `_load_detail(fast=True)`，**不写整本缓存** |
| `app/engine.py` | `verify.ok` 埋点新增一格 `不全=(r.chapter_note[:24] or "-")` —— 目录不全从"只有日志里才有"变成账本上看得见 |

## 四、举一反三

### ① 同类站还有几个？—— 按目录模板形状数（不猜）

长书能不能被完整取到，取决于"目录模板的末段是不是独立的页码槽"。
库里 433 个站点按 `toc_tpl` 的形状分：

| 形状 | 站点数 | 说明 |
|---|---|---|
| 多段数字槽（`/html/#/#/`、`/book/#/#/`、`/read/#/#.html`） | **46** | 就是今天修的三种形状的家族，长书此前**必然被截** |
| 单段槽（`/book12345.html`） | 17 | 分页多为 `_2.html`，已由 `_paged_siblings` 覆盖 |
| 其他 | 370 | 无分页或模板已含"第N页"占位 |

**46 个站点（10.6%）** 属于今天这条缺陷的影响面 —— 它们不是"坏了"，
是"长书只能下到前十来分之一"，而且账本永远绿。这也是为什么今天 12 本探针里
有一半的章数都停在 100 出头。

### ② 为什么这条判据以前没抓到它

`tools/test_toc_full.py` 原本 101 条断言，**没有一条**喂过"带分页器的目录页"。
夹具都是单页目录（20~200 条），于是"拼分页"这条路在测试里**从未被走过**。
判据覆盖的是"单页能不能抽全"，不是"跨页能不能拼全" —— 一个连测试都没设想过
的页面形状，自然不会红。今天补的 D 组就是这一份：三种形状各 4 条断言 +
一条反证（**只有章节链接、没有分页器 → 不许认出下一页**）。

### ③ 顺带补掉的两个"沉默"

* `_merge_paged` 收尾原来只在撞页数时置 `pending`，墙钟/模板不符静默 → 现在三种都置；
* `verify.ok` 原来只有章数没有"全不全" → 现在带 `不全=`。
  11-21 的教训是"循环里 except 只打 debug 等于让账本撒谎"，今天是同一母题的另一处。

## 六、欠账

1. **实例恢复后第一件事**：核对线上 md5，补 ship，然后在线上验一次
   `verify.ok ... 不全=-` 与"长书章数 > 500"。

   外层 `fast_mode` 不改变缓存 key，缓存命中也重解析。**并发竞态不是新增成本**，
   但它会让"打开一本书"偶发卡死，得给 `page_of` 加单飞（同一个 URL 只跑一轮分页）。
