## 二、主线：**自有来源（30 个已学会的站）每次搜索都在半路被扔掉**

### 2.1 现场

`search.done` 里 `未回` 那一格，11-06 的 17 次搜索里有 **12 次**点着 `registry`：

```
未回=2(registry,wyshu)   ×5
未回=1(registry)         ×3
未回=4(registry,wikisource,wyshu,xbqg5200)
未回=4(kunnu8,registry,wikisource,wyshu)
未回=3(kunnu8,registry,wyshu)
未回=2(kunnu8,registry)
```

`registry` 就是 `RegistrySource` —— 库里 30 个「已学会站内搜索」的站，**一次扇出全问一遍**。
它被判「未回」，意味着这 30 个站的结果**整批作废**。

今晚 22:38 真机复现（线上服务，`discover=0 probe=0 sample=0` 只测扇出）：

```
22:38:12 搜索收手：已返回 3/7 个源（43%）、原始 21 条/推给前端 7 条（其中确切 1 条）、
         耗时 4.5s，放弃 4 个还没回来的慢源（registry, wikisource, wyshu, xbqg5200）
22:38:12 search.done 书名=三体 候选=1 可读=0 答=3/7 未回=4(registry,...) 源池=30→29
```

同一时刻、同一个库，**单独**调它（服务器上直接跑 `RegistrySource().search()`）：

```
三体        → 40 条, 3.52s
顾漫        →  8 条, 7.05s   （骄阳似我 / 微微一笑很倾城 / 杉杉来吃，都带作者）
骄阳似我    →  7 条, 5.92s
```

也就是说：那 40 条、那 8 条，**在我们自己手里，只是被扔了**。
对《三体》影响还算小（别的源也给了一条）；对**作者搜索**和冷门书是致命的 ——
库里 30 个站恰好是「我们自己学来的独有召回」。

### 2.2 根因：三层，缺一不可

**① 它自己声明的预算比人家的收手点还长。**
`SEARCH_BUDGET = 7.0`，而引擎 `SEARCH_SOFT_DEADLINE = 6.0`；
更早的收手点 ③（有确切命中 + 已有 2 个源答话 + `SEARCH_GRACE = 3.5`）才是线上常态 ——
今晚这次就是 **4.5s** 收的手。一个声明要 7 秒的源，在 3.5~4.5 秒必然被判「未回」。

**② 「够用了」这条判据看不见「还有源在自己的预算里跑着」。**
②（答源占比 0.75）和 ③（宽限期到）只认「已答几个源」，不认「谁还没答、它本该跑多久」。
30 个站 vs 6 个预置源，占比一到就收，**最贵的那个源永远轮不到**。

**③ 连接池只有 10 条，30 个站被压成 3 批串行。**
`utils._make_client` 是 `max_connections=10`，而 `SEARCH_WORKERS=24`。
30 个站 → 3 波，每波都要等上一波。这就是它为什么要 7 秒的直接原因。

单站耗时实测（26 个可搜站，今晚）：

```
p50=1.18s  p80=2.48s  p90=3.86s  max=7.33s（www.taiminc.com）
>2.5s: 5 个   >3.5s: 3 个        ← 而这 3 个的产出是 0 条 / 报错
```

把连接池放大到 32 之后，同一个查询从 **7.05s → 4.37s**。

### 2.3 修法

| 文件 | 改动 |
|---|---|
| `app/sources/base.py` | 新增 `Source.budget_s`：源可以**声明**「我内部要跑几秒」。收到声明后，引擎的 ②③ 必须让路（④ 软截止仍是无条件兜底）。 |
| `app/sources/registry_source.py` | `SEARCH_BUDGET` 7.0 → **5.0**；新增 `budget_s = SEARCH_BUDGET`。 |
| `app/utils.py` | 连接池 10 → **32**（keepalive 5 → 16），提成 `POOL_MAX_CONNECTIONS / POOL_MAX_KEEPALIVE` 便于断言。 |
| `app/engine.py` | 新增 `_honored()`：算出「还没回来、但还在自己声明预算里」的源；②③ 加 `not _wait_honored` 守卫；收手日志新增「按自身预算等过 X」。 |

代价：冷门书最多多等 ~1.5s（3.5s → 5.0s），换回 30 个站的产出。
**不让路的那条（①：真的攒够 12 条确切命中）保持原样** —— 那种情况多等一秒是纯损失。

### 2.4 判据

- `tools/test_search_recall.py` 新增 H 组（11 条），三个场景互为反向：
  - **H1** 宣告了 `budget_s=0.7` 的慢源：它那条结果必须进最终结果，收手日志必须写「按自身预算等过 …」；
  - **H2** 同样慢但**没宣告**预算：必须照旧 0.12s 收手、它那条被弃（保护只发给声明过的源）；
  - **H3** 宣告了但**已过期**：不许再等（否则声明值等于无限期）。
- `tools/test_source_budget.py` 新增 ⓿ 组（8 条）**结构性一致**：
  声明值 ≤ 软截止、`budget_s` 必须等于它真正在用的预算、总预算 < 软截止、
  单站超时 < 总预算、**连接池 ≥ 扇出并发**。这类矛盾单看任何一处代码都看不出来，
  只存在于两个常量的大小关系里。

## 三、举一反三

### 3.1 同类源会不会也中招？

会，而且是同一批老面孔 —— 但**故意不保护**：

| 源 | 内部预算 | 为什么不等它 |
|---|---|---|
| `wyshu` | 6.0s | 索引要抓 8 个分类，线上常态是「到点收手、0 本」；为它把每次搜索都拖到 6s 不划算 |
| `wikisource` | 6.0s | 187s 病灶修过之后仍然慢，且只覆盖公版书 |
| `xbqg5200` | — | 多半在熔断里，本来就不进分母 |

这是一条**取舍**而不是遗漏：`budget_s` 是「按源声明」的，只发给「产出确实独有」的源。
将来若要给 `wyshu` 也加，先量「为它多等的秒数 ÷ 它救回的条数」。

### 3.2 这条判据为什么没抓到它？

因为**账本是自洽的**：`答=3/7 未回=4` 加起来正好等于 7，恒等式全过；
`候选=1 可读=0` 也解释得通（"这本书只有一条候选，还是死链"）。
缺的不是算术，是**一个事实字段**：这个源没答话，是"它慢到超时"还是"我们提前不要它了"。
今天补的就是这一格 —— 收手日志现在会写「按自身预算等过 registry」，
预告"这笔多花的时间是故意的"。

### 3.3 顺带发现的第二件事：一次搜索废掉 4 个模板（`源池=30→29`）

同一次 22:38 的搜索里，四个站被连记三次「打开的不是搜索页」而作废模板：

四个都是 `MEMORY.md` 里已定性的「四类病因、同一条判据」。11-06 上的
`tpl_dead + 7 天冷却` 正在生效（日志已写「该站累计被判死 1 次」），
所以这是**判对了**，不是错杀 —— 今天不动它。
