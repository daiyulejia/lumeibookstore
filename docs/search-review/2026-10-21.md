## 二、死在哪一段

四段链路逐段判：

- **① 站内搜（7 个源）→ 全灭**。当时 403/peer-closed 集中在"真有这本书"的两个源上：
  `xbqg5200 HTTP 403`、`www_xbiquge_info: peer closed connection`；
  其余 5 个源（gutenberg/wyshu/kunnu8/wikisource + registry）对这本书本来就 0 条。
- **② 联网发现 → 起了，但没产出**：4 次都触发了 `search.web.preempt`（1.7s / 3.9s / 6.5s），
  当轮 `联网发现=0`。
- **③ 核实书页 → 10/15 失败**：`www.qidian.com HTTP 202`（JS 挑战）、
  `www.qidiy.com 403`、`m.kudushu.org 403`。候选地址打不开 = 一律丢弃。
- **④ 正文可读性**：未走到（没有候选）。

结论：死点在 **① 站内搜全灭 → ③ 核实又全被拦**，两者同时发生才出 0 条。

## 三、根因（服务端实测，不是推测）

**根因 A：`wikisource.search()` 单次要 186.9 秒 —— 源自己没有时间上限。**

```
$ .venv/bin/python -u _probe_one.py wikisource 青叶灵异事务所
返回 0 条，耗时 186.9s          ← 修复前
返回 0 条，耗时 7.2s            ← 修复后（同一台服务器）
```

机制：`_api()` 是「5 次重试 + 递增退避（1.0/2.5/5/8.5/13s）」，每次握手还要
connect 12s；`search()` 又串两次查询（`intitle:` 一次、全文一次）。
这台机器到 `zh.wikisource.org` 的 TLS 握手**天天超时**（当天日志 117 次
`The handshake operation timed out`）。

后果不是"它自己慢"，而是**别人的搜索变 0 条**：引擎 20s 收手后线程还活 167 秒，
占着线程池和连接（共享 httpx client 只有 10 个连接）。

**根因 B：卡死不返回的源，熔断器永远学不到。**

熔断器只统计「跑完、但抛了异常」的源（`_run` 里的 `take_error`）。而卡死的源
future 永远不完成，`_run` 走不到 `note_fail` → 每轮搜索它还在名单里，再吃 20 秒。
量化：当天 wikisource 失败 117 次，**熔断只触发 1 次**（还是我在 09:16 手动探测时触发的）。

**根因 C（判据缺口，不是产品 bug）：`search.done` 只有「候选=0」。**
「书真的没有」和「源全挂了」在日志里长得一模一样，而处置完全相反
（前者补源 / 记 known-missing，后者等几分钟重试）。今天复盘只能靠几行散落的
403 / 握手超时反推，白烧半小时。

**还发现一个同类（本次未修，记待办）**：联网核实的失败率 **10/15 ≈ 67%**，
全是 403 / HTTP 202（qidian 的 JS 挑战页）。它不产生"0 条"（有本地结果时不影响），
但"本地全灭 + 联网"这条唯一的救命路上，三分之二的候选是打不开的。
已列入下一轮：核实阶段按 host 的 403 记录降权 + 提高可核实站的优先级。

**这条判据为什么没抓到它？**
- 熔断器：**埋点漏项** —— 只量"跑完的失败"，不量"没跑完的"。已补（见下）。
- `search.done`：**压根没埋** —— 只有结果数，没有源的健康账。已补。

判据三问自检：
1. **会不会只因环境变**？不看耗时，看**请求次数**（过期 deadline 必须 0 次）和
   **第二次查询发没发**（186 秒就是它串出来的）—— 与机器负载无关。
2. **把功能拆掉这条还绿吗**？`mutate.py hung` 三条全部被抓住（见下）。
3. **只验正向没验反向**？有反向：`test_source_health` 里同时断言"空结果的源不许被熔断"、
   "正常源每轮都还在被调用"，防止修成"搜冷门书把所有源拉黑"。
