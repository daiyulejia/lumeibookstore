## 三、根因

`app/engine.py` 收手四门：

```
① _tight_ok and len(raw) >= SEARCH_ENOUGH                 ← 没有 not _wait_honored
② _tight_ok and not _wait_honored and answered_ratio>=0.75
③ _tight_ok and not _wait_honored and 已答≥2 and 过了宽限
④ elapsed >= SEARCH_SOFT_DEADLINE                          ← 唯一无条件兜底
```

11-09 给 ②③ 加了「还在自己预算里就让它跑完」的门，**① 被漏了**，注释给的理由是
「真的攒够 12 条确切命中，多等一秒是纯损失」。可它数的其实是 `len(raw)` ——
**原始候选条数，撞词也算**。于是「11 条噪声 + 1 条确切」在 1.5s 就能成立。
这是 10-24「够多≠够好」那个洞的最后一个入口，也是 11-15 记下的欠账原文
（"引擎收手 ① 不看任何源声明的预算，1.5s 就收手"）。

### 修复

- ① 补 `not _wait_honored`：四条门的让路语义统一（④ 仍无条件兜底）。
- 抽出 `_wait_note()`：**「等过 X」（已交卷）与「X 等满预算仍未回来」（被切断）
  分成两句，两笔账互斥**；墙钟收手行也带上这句（原来只有「够用了」那行有，
  于是"墙钟切断了谁"永远看不出预算状态）。

### 反证

`tools/mutate.py` 新增 2 条靶点（① 让路、日志口径），组「源预算让路」：

```
✓ ① 「原始条数够」不再给声明预算的源让路  → 红在 H4 两条
✓ 收手行把「等过」和「等到头仍未回来」混成一笔 → 红在 H5 两条
突变 8 条 · 问题 0 条 · 源码已逐字节还原 ✓
```

## 四、举一反三

### Q1：同类源会不会也中招？

`grep "budget_s = "` 全仓只有 **1 处**（`RegistrySource`），所以**没有第二个同类受害者**。
但反过来要问：**其余 7 个源为什么不声明？它们真的不需要吗？** 逐个实测（搜「三体」，12s 上限）：

| 源 | 耗时 | 产出 | 该不该声明预算 |
|---|---|---|---|
| kunnu8 | 1.42s | 1 条 | 不用（3.5s 宽限内交卷） |
| xbqg5200 | 1.05s | 12 条 | 不用 |
| www_xbiquge_info | 0.87s | 20 条 | 不用 |
| wyshu | 0.00s | 0 条（索引冷，后台建） | 不用（11-15 已定：不做同步建） |
| wikisource | 6.19s | 0 条（SSL 握手超时） | 不该（空手，声明只会更慢） |
| gutenberg | 8.05s | 抛 `RuntimeError` | 不该（熔断器管这个） |

→ 结论：**其他源不声明是对的**，这次的影响面就是 registry 一个（且它出现在几乎每次搜索里，
所以实际影响 100% 的搜索：3/10 次真被切断，其余是它在 1.8s 内自己答完）。

### Q2：这条判据为什么没抓到它？

三个都占：

1. **清单漏项**：H 组场景（`recall_h_*`）里 3 个快源各只回 1 条 → `raw=3 < SEARCH_ENOUGH(12)`，
   **① 从来没被触发过**。H1 只验了 ②③。
2. **判据太松**：没有任何断言检查"放弃名单"与"等过名单"是否重叠——那行自相矛盾的日志
   在线上/本地存在了 10 天，没有一条测试读它。
3. 不是没埋点（`waited_for` 有，`_honored` 有），是**没把两笔账分开写**。

补法：`test_search_recall.py` 加 H4（原始条数够 + 预算源还在跑 → 必须等它，且日志不许自相矛盾）
与 H5（让路到软截止 → 必须写「等满预算仍未回来」），两条突变各验证一次。
