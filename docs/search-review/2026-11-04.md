## 二、主线根因：新请求被交给「已经被放弃的那一轮」

### 现场

11-02 01:25:19 起 `你腿真美`，01:25:21 又来一个同名请求。日志把它们写成两件互不相干的事：

```
01:25:19 req=rkhi search.start 书名=你腿真美
01:25:20 req=o698 POST /api/confirm 200 ms=177     ← 确认框弹出
01:25:21 req=gd51 search.start 书名=你腿真美        ← 用户点了「就搜《你腿真美》」
01:25:21 req=rkhi 客户端已断开，扇出收手：已返回 1/5 个源
01:25:21 req=rkhi search.done 候选=0 aborted=True 合并=2 耗时ms=1507
```

`合并=2` 说明**确实有两个订阅者**，可整轮还是收手了 —— 按 11-01 的设计
（"单人走 ≠ 整轮停"）这本不该发生。

### 时序（为什么两个订阅者也救不回来）

1. 请求 B 进 `search()`，`_FLIGHTS.acquire()` 在**处理函数里**跑，此刻 A 那一轮还活着 → 拿到同一个 flight；
2. 前端 abort A → A 的生成器被 close → `leave()` 看到 `_subs` 已经空 → `_abandoned=True`、`_stop` 置位；
3. B 的 `subscribe()` 要等生成器第一次 `__anext__()` 才跑（中间隔着"把响应头发出去"这一跳）——
   它挂到一具尸体上，`joined` 变成 2；
4. 引擎下一次判 `should_stop()` 立刻收手 → B 拿 `候选=0`。

所以 `合并=2 + aborted=True + 1.5s` 这个组合本身就是**症状**：不是客户端走了，
是我们把新请求交给了已经死掉的那一轮。

### 根因的根因：确认框把同名搜索掐掉重来

`/api/confirm` 是**按输入防抖**（320ms）触发的，而搜索是提交时就起的。
于是搜索跑到 1.3 秒左右，「你找的是不是《你腿真美》？」正好盖在结果页上弹出来，
用户一点「就搜」，正在跑的那一轮被 abort、从头再来一遍。

当晚 13 次搜索里 **10 次**是这种「同名第二发」（间隔 1~2 秒）：

```
01:23:52 / 01:23:54  情欲超市全集
01:25:19 / 01:25:21  你腿真美
01:26:31 / 01:26:32  虚空塔
01:27:05 / 01:27:06  情欲超市全集
01:27:40 / 01:27:41  你腿真美
```

### 修法

- `app/searchflight.py`
  - `Flight.subscribe()`：**已放弃**的一轮返回 `None`，不许往上挂；
  - 新增 `FlightBook.subscribe(key, factory, loop)`：把「拿一轮 + 挂上去」收进同一把锁，
    两步之间不再有缝；弃轮/结束轮顺手摘牌，拿不到就现建一轮。
- `app/main.py`：请求路径改走原子接口；runner 用 `_holder` 读**自己那一轮**的 `joined`
  （原来读闭包外层的 `flight`，弃轮与新一轮的合并数会混成一个）。
- `app/static/js/discover.js`：正在搜同一个书名时，确认框**不弹**、「就搜」**不重启**。
  换词（`d.keyword !== M.confirmed`）照旧走确认流程，不影响防打错的功能。

## 三、同类问题还会不会复发（举一反三）

### ① 同一族"两次调用之间状态变了"还有没有别处？

`acquire` 与 `subscribe` 是唯一一处「先查状态、后动手、中间隔着一次 await / 一次 IO」的地方。
`runFetchUrl` 和 `toggleSource` 也会 abort 当前搜索，但那是**换目标**（另一个书名 / 另一个地址），
本来就该重来，不是这个 bug。现在用判据钉住接线：
`test_search_flight.py` ⑨ 断言 `main.py` 里有 `_FLIGHTS.subscribe(`、且**不再有** `_FLIGHTS.acquire(`。

### ② 这条判据为什么没抓到它？

不是清单漏项、也不是太松 —— `aborted=True` 这个字段**一直在**。
漏的是**组合**：`合并>1` 却说"客户端已断开"，这在语义上自相矛盾，但没人把它当异常。
现在从结构上排除了（弃轮不可能再获得订阅者），所以不需要再加一条"看着像异常"的启发式。

### ③ 顺带查到的：一轮搜索把源池吃掉 5 个

上线后验收那一轮 `源池=32→27`，5 个站被"连续 3 次打开的不是搜索页"判死：
`www.itiandixs.com`、`m.kudushu.org`、`www.xuanhuanbiquge.com`、`www.xizids.com`、`www.jcxs.cc`。

**逐个抽查（担心又是一次错杀）：**
`www.jcxs.cc/modules/article/search.php?searchkey=…` 搜《三体》和《斗罗大陆》
都只返回一张**空表**（`<tr>` 1 行、0 个书链接、关键词不回显）——
模板确实不工作（杰奇 CMS 多半只认 POST），**判定正确，不是错杀**。
另外四个站同一轮同时死、且 `search_hit=0`（从来没搜出过东西），符合"模板真坏"。
→ 源池 32→27 是真实清理；学站器会按新逻辑重学。
