## 二、今天真正的病灶：`确切=` 会说谎（联网救回的正主被记成 0）

线上与本地复现完全一致：

```
search.done 书名=我们猫猫不能听这些 候选=1 成书=1 可读=1 确切=0
books[0]    title=我们猫猫不能听这些  tightness=1.0  tight=true
                    ↑ 同一份数据里，书说自己确切，账说自己不确切
```

「候选=1、确切=0」**在算术上就不成立**。

**根因**：`确切` 取的是扇出阶段的累加值 `tight_streamed`，而**联网兜底交回来的
条目压根不经过那个循环**（`_discover` 直接 `rank(results + extra)`）。于是
"本地全灭 → 联网救回"这条最惊险、最需要复盘的路径，永远被记成"零正主"。

**为什么必须今天修**：昨天日报的欠账①（要不要"零确切就联网"）就建立在这个
传感器上。传感器坏着去定规则，定出来的规则一定是错的 —— 比如「确切=0 就联网」
会对**已经救回来**的那一轮再烧 10 秒联网预算。

**修复**：`tight_hits` 改成 `sum(1 for r in results if r.tight)`，与 `候选`
（`len(results)`）数同一个集合；扇出阶段的累加值另存 `tight_streamed`，
收手判据继续用它。口径钉死：

```
确切 <= 候选，且 确切=0 ⟺ 结果里没有一本是这本书
```

上线后同一本书：`候选=1 确切=1`（耗时也从 12.9s 降到 4.2s，因为 wikisource
这轮被熔断跳过了）。

## 三、顺带修掉的两处「账说不清 / 日志说反话」

### ① 被熔断跳过的源不进账 → 全灭时是 `答=0/0`

「目标源全在熔断」算出来是 `候选=0 答=0/0 耗时ms=2`：分母是**过滤后**的源数，
所以这行账加得起来、却没有信息量，和"搜遍了都没有"长得一模一样。

修：源账加第五格 `熔断=N(名字)`，`sources_total` 含被跳过的源（它们是"该搜而没搜"），
且全灭时明写一句。上线后真机：

```
跳过 1 个熔断中的源（wikisource），剩 0 个照常扇出
本轮一个源都没能搜：目标源全部在熔断中（wikisource）——结果为空不代表没有这本书
search.done 书名=三体 候选=0 答=0/1 挂=0 未回=0 熔断=1(wikisource) 耗时ms=2
```

顺手补：`sources=xxx` 指定了一个**不存在**的源名时，以前连日志都没有，现在单独记一句。

### ② 联网兜底「说了跳过，然后照样跑」

```
elif web is not None:
    logger.info("跳过联网兜底：总预算已用完")   ← 说跳过
    extra = self._discover(...)                ← 又跑了
elif web is not None:                          ← 死分支，永远到不了
    logger.info("跳过联网兜底：总预算已用完")
```

后果两个，都不报错：日志撒谎；`over_budget` 按 32s 算，真跑起来就是
"承诺 32 秒、实际 42 秒"。修：真的不跑，日志写「本轮不联网」，
并记 `stats["web_skipped_budget"]`；删掉重复死分支。

### 判据为什么没抓到它

不是清单漏项、也不是判据太松 —— 是**埋点算错了对象**：`确切` 埋在了扇出循环里，
而不是埋在"用户最终看到的那批结果"上。而 `test_search_recall.py` 的场景②③④
**全部是 `discover=False`**，联网路径一次都没进过测试 —— 覆盖漏项。

补的判据：
- 场景⑤：本地全空、只有联网那条正主 → 断言 `tight_streamed=0`（证明差值只能来自联网）
  且 `tight_hits=1`，再加一条对账 `确切 == sum(结果里 tight 的条数) and 确切 <= 候选`。
- 场景 C：全在熔断 → `熔断=1(ledger_403)`、分母=1、五格加得起来、日志必须吭声。
- 场景 D：预算用完 → 联网源**调用 0 次**、`web_skipped_budget=True`、日志说「本轮不联网」。

## 七、欠账（明天要回答的）

1. **死源的复活成本 & 退避为什么总涨不上去**。今天实测：只搜 wikisource 一个源，
   失败要 **9.4s / 7.1s**（它自己的 6s 预算 + 多次 SSL 重试）。
   更要紧的是机制：09:47 部署重启后，`cache/sourcehealth.json` 里两条记录
   的 `until` 已过期 → `_ensure_loaded()` 按设计**直接丢弃**（"只收仍在冷却中的"）
   → `streak` 归零 → 于是 09:49 那次失败只记 `fails=1`（不熔断）、09:50 才熔断，
   而且退避**从 15 分钟重新开始**。死源因此永远涨不到 8 小时封顶 —— 昨天
   "落盘 + 指数退避"只对**没被重启打断的**那段窗口有效。
   要改就得动 `_ensure_loaded` / `_save` 的"过期即丢"语义，而
   `mutate.py [backoff]` 里有一条断言钉着相反行为（"过期条目不许进内存账本"，
   当初是为了避免幽灵记录）。这是设计取舍，明天留足时间再做，别顺手改。
2. **`streamed`(45) 与 `kept`(~28) 双门槛**：`kept>0 但 streamed=0` 时，
   fan-out 会按 20s 硬上限等（今天一例 ~1.2s 白等）。先量这种轮次占比，
   再决定是调 `STREAM_FLOOR` 还是给收手判据加一个"最终能留下"的口径。
