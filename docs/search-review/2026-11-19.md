## 三、主线根因：两个引擎死一个 + 只问一句话

### 3.1 百度整个引擎不可用，而且**静默**

实打三组请求（本机）：

```
GET https://www.baidu.com/s?wd=我的阿勒泰  → 200，**2649 字节**，<title>百度安全验证</title>
GET https://www.baidu.com/s?wd=遥远的救世主 → **302**（跟随重定向后仍是那张验证页）
先 GET https://www.baidu.com/ 取 BAIDUID cookie，再搜 → 仍是 2649 字节验证页
GET https://m.baidu.com/s?word=…           → 302
```

即：这个出口 IP 被判成机器人，**换 UA / 换 cookie / 换移动端入口都无效**。

旧代码怎么处理这件事：

```python
if r.status_code != 200 or len(r.text) < 5000:
    return out          # ← 和"一条都没搜到"返回同一个 []
```

于是全链路只剩下聚合行 `百度=0`。这条日志读起来是"百度没这本书"，
事实是"百度这个引擎整个没了" —— 一边是少一半候选，一边是网上没有这本书，
**处置完全相反**。而它确实少了一半：`引擎=bing5,baidu2` 里那 2 条，
是历史遗留路径上才有的，正常搜索里百度贡献的是 0~8 条（11-13 的历史日志里
`百度=3/4/5/7/8` 都出现过）。

对照网上那本"全网只有 1 个可用站"的书：Bing 只认书名时第一屏 10 条里有
8 条是百科/影视/豆瓣（被噪声表滤掉），剩 1 个 youyiyan，而它也不是目录页。

### 3.2 修法一：让"被拦"和"没结果"分开（`app/websearch.py`）

- 新增 `EngineBlocked(RuntimeError)`：这是"对方拒绝了我们"，不是"没有结果"。
- `_baidu()` 三种结局分开：
  * 验证页（带指纹 **且** 体量 < 20KB）→ 抛 `被反爬（HTTP 302，2649 字节验证页）`，并**短期负缓存 600s**；
  * 非 200 → 抛 `HTTP xxx`；
  * 1~5KB 的空壳（既不是结果页也没有验证字样）→ 抛 `返回异常页（N 字节）`；
  * 只有"正常大页面 + 一条 mu 都没有"才返回 `[]` —— 那才是"没这本书"。
- `find_book_pages()` 的 `except` 分支本来就会把它记进进度日志，于是现在会看到
  `百度 搜索失败: EngineBlocked: 被反爬（HTTP 200，2649 字节验证页）`。
- 负缓存只为三件事：不越打越死、不把同一件事刷几百行、**省掉每个搜索白等一次**。

判据里专门有一条**反向**：30KB 的结果页里夹着用户帖子标题「请输入验证码」，
**不许**判成被反爬（真验证页只有 2.6KB）。指纹与体量缺一不可。

### 3.3 修法二：候选太薄时换一种说法再问一次（同文件）

实测量出来的差别（同一个 Bing，只换查询串）：

```
我的阿勒泰              → 可用站 1 个（maiguiread，只有简介）
我的阿勒泰 小说         → 可用站 4 个（qidian / tianyabooks / zishiba / maiguiread）
遥远的救世主            → 可用站 2 个
遥远的救世主 小说       → 可用站 3 个（fanqienovel 在其中，**实抓 33 章**）
```

于是：`if 第一轮候选 < 4: 用「书名 小说」再问一遍，合并`。

- 门槛是**计数**，不是耗时（不随机器负载漂）；
- 候选够多（≥4）就**不问** —— 核实是这条链上最贵的资源（每个候选开一次页、10s 上限），
  11-04 的教训就是"给核实喂噪声等于把真书页挤掉"；
- 第二轮**不重置** `per_host` 与去重集合：同一个站不能靠两次问法占走 4 个名额；
- 账本新增一行：`联网候选（第二次问法）: 第一轮=1 加问=《遥远的救世主 小说》 新增=2 合计=3`。

**端到端实测（本机，改完当场跑）**：

```
百度拒绝了我们（HTTP 200 / 验证页 2649 字节），10 分钟内不再试
联网候选: 去重前=1 取=1 各引擎=Bing=1 百度=0
联网候选（第二次问法）: 第一轮=1 加问=《遥远的救世主 小说》 新增=2 合计=3
联网发现命中: fanqienovel.com 33 章 (质量 1.00)
```

《遥远的救世主》从 `候选=0` 变成 **33 章可读**。

另外两本（我的阿勒泰 / 乡土中国）**仍然 0**，如实记：
候选从 3 条涨到 5 条、7 条降到 5 条，但新增的站（tianyabooks / zishiba）
**连不上**，99csw / academia 仍是 403/Cloudflare —— 属于
`known-missing.md` 里已记的「打不开，不是没有」。我的阿勒泰 10-31 修好的
`cn.shubaoc.com/novel/bpo/` 今天**本机 DNS 解析不了**（`getaddrinfo failed`），
无法确认那条修复今天是否仍有效，不据此改判定。

## 四、副线：`site.revive` 对"第一次见到的站"说谎

线上 11-18 23:06 那批日志里，三条自相矛盾的记录：

```
site.revive 域=m.laidula.com 名=m.laidula.com 成功=0 挂=1 原因=成功一次
site.revive 域=epolyswindows.en.alibaba.com  成功=0 挂=0 原因=成功一次
site.revive 域=3g.jiangxian.yukaplay.top     成功=0 挂=0 原因=成功一次
```

成功 0 次、挂 1 次，却说"靠一次成功复活"。根因：`is_healthy({})` 对**空记录**
返回 False，于是新站的第一笔账只要不是失败，就被判成"越过死亡线回来了"。

危害不只是日志难看：11-17 的试用通道就是拿 `site.revive` 当**验收判据**
（"站点靠哪一次成功回来的"），新站噪声一多，这条判据就废了 —— 与
11-06「学会了≠这个站行了」、11-11「闸门装在一个入口上等于没装」同一母题。

修法：先判有没有旧账（`is_new = not cur`），**有旧账才谈得上"变了"**。
新站第一笔账照常记，只是不打升降级。老站越线后靠一次成功回来，仍然必须打。

## 五、举一反三

**同类站/同类源会不会也中招？**

| 同类 | 预计影响 | 逐个验了什么 |
|---|---|---|
| 另一个搜索引擎 | 1 个（Bing） | Bing 未拦，但**只认书名**时第一屏 8/10 是百科/影视 → 靠 3.3 的第二问补 |
| 其它"静默返回空"的入口 | 2 处 | `_baidu` 的 1~5KB 空壳（也抛了）；`_bing` 的 `status != 200` 仍返回 `[]`（**未改**，见欠账） |
| 其它"首次登记即判升降"的入口 | 1 处 | 只有 `note_site` 一个入口，已修 |
| 试用通道的验收判据 | 全部 | 依赖 `site.revive`，现在只剩真爱活 |

**这条判据为什么没抓到它？** 三个都不是产品逻辑写错，而是**没人量**：

1. **清单漏项**：`_baidu` 的"被拦 vs 没结果"从来没进过任何测试 —— `test_websearch.py`
   整份都在测**名额分配**（Bing 的噪声会不会吃光名额），没测过"引擎本身没了"。
2. **判据太松**：`if status != 200 or len < 5000: return []` 把三种完全不同的结局
   （被反爬 / 无结果 / 空壳）合成一个返回值，下游再怎么埋点也分不开。
3. **压根没埋点**：`is_new` 与否，代码里原来没有任何变量表示它 —— 只能从
   `first_seen == updated` 事后反推，而复盘时没人会想到去反推。

判据三问：
1. **会不会只因环境变？** 全是假引擎 / 假 HTTP 响应，不碰网络、**不含任何耗时阈值**；
   两轮问法的门槛是"候选条数 < 4"这种纯计数关系。
2. **把功能拆掉这条还绿吗？** 见下节反证，3/3 全红。
3. **只验正向没验反向？** 每条都有反向：候选 ≥4 **不许**加问、同一站跨两轮**不许**翻倍、
   大页面夹验证字样**不许**判被拦、新站**不许**喊复活、正常页**必须**抽出候选（不是恒抛）。
