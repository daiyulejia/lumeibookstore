## 二、主线：一个健康的站，被我们自己的保护机制越封越久

既然没有线上流量，就顺着「今天本地实例日志里当场复发的东西」查。
`logs/server-2026-11-16.log`（22:47 启动那一份）+ `logs/app.log` 09:51 那一段，
拼出一条**自噬循环**：

```
09:51:31  xbqg5200 返回空壳页面（59 字节），判定为限流并进入冷却 120s
09:51:33  source.fail 源=xbqg5200 原因="RuntimeError: 该站点刚被限流，冷却中（还剩 118s）"
09:51:48  WARNING 源 xbqg5200 连续失败，熔断 5 分钟（…冷却中（还剩 104s））
```

链路四段（用本项目自己的口径）：

| 阶段 | 发生了什么 | 正常吗 |
|---|---|---|
| ① 站内搜 | 打太快，站返回 59 字节空壳 | 站没错，是我们快 |
| ② 本地保护 | `mark_blocked(host, 120s)`，冷却期内 `fetch_text` 一个请求都不发，直接抛错 | **对的** |
| ③ 引擎归因 | 把它当"源抛异常" → `HEALTH.note_fail()` | **错** |
| ④ 熔断 | 3 次记满 → 全局熔断 **300s**（冷却只有 120s）→ streak+1 → 下次 10 / 20 / 40 分钟 | **错，而且自我强化** |

**根因一句话：`utils.fetch_text` 的「同域限流冷却」是我们自己的保护机制，
引擎把它当成了「源挂了」。**

后果有三层，缺一层都不足以解释它为什么能活这么久：

1. **熔断比冷却还长**（300s > 120s）：冷却早过了，熔断还没过 → 一个只是
   "我们打太快"的站被全局判死 5 分钟起。
2. **退避会累计**：`trial` 到期放出来试探 → 一进去又撞冷却 → 立刻重新熔断
   → `streak+1` → 10 / 20 / 40 分钟 → 封顶 8 小时。**越保护越死。**
3. **日报被污染**：账上写 `挂=xbqg5200`，读起来是"这个站坏了"。
   两者处置正好相反：一个是"换源"，一个是"降速、等它"。

### 举一反三

**① 同类源会不会也中招？—— 会，而且是全部。**

| 影响面 | 数量 | 为什么 |
|---|---|---|
| 内置源模块（走 `fetch_text`） | 9 个文件（adapter / configured / gutenberg / kunnu8 / registry_source / template_source / web / wyshu / xbqg5200） | 冷却判定在 `fetch_text` 内部，所有调用方共享 |
| 来源库里全部已学模板 | 全部（复用 `template_source`） | 同上 |
| 榜单来源 | 7 个来源 × 7 类 | `ranks._fetch_source` 走同一个 `fetch_text` |

触发条件也不罕见，`mark_blocked` 有两个入口：
- `utils.py` 连接建不起来（`_CONNECT_DEAD`）→ **90s**
- `xbqg5200` 空壳页 → **120s**

也就是说：**任何源一次网络抖动**（连接被断）都会让自己进 90s 冷却，
而冷却期内每搜一次就多记一次"连续失败" → 3 次 → 5 分钟。
不是 xbqg5200 特例。

逐个验（真实源，不是假源）：把 `https://www.xbqg5200.com` 关进 60s 冷却，
再用**真实源实例**搜一次《三体》：

```
账本 = {'答': '0/1', '挂': '0', '未回': '0', '熔断': '0', '自限': '1(xbqg5200)', '卡满': '否'}
sources_failed = 0 []
sources_selfthrottle = 1 ['xbqg5200']
熔断器是否开了 = False
```

榜单侧同样验过（`ranks._fetch_source`：三轮自限流 → `ranks:xxx` 未被熔断；
反向：真挂三轮 → 必须熔断）。

**② 这条判据为什么一直没抓到它？—— 缺口在"归因维度"，不是清单漏项、也不是判据太松。**

- 埋点不是没有：`source.fail` 一直在打，原因文本里甚至写着"冷却中"。
- 但 `挂=` 是**混装桶**：403 / 超时 / 找不到搜索框 / 我们自己限流，全在里面，
  日志里没有任何字段能让日报把它们分开。所以每天看着 `挂=xbqg5200`
  都得出同一个错误结论。
- 熔断器的 `classify()` 也只有 `net` / `other` 两类 —— 同样没有"本地保护"这一档。
- 旧测试的 26 处断言全在问"连调 N 次会不会熔断"，**没有一条问"这次失败是
  谁造成的"**。这是判据的缺失维度，不是松或紧。

## 三、副线：榜单「必然少一类」，是算术没平

同一条日志的另一半：

```
[ranks] xbiquge allvisit 抓取失败：…(The read operation timed out)
[ranks] xbiquge-lastpost postdate 抓取失败：…(The read operation timed out)
[ranks] 刷新超预算（25s），先收手：已完成 6/7，还欠 1 类（lastupdate）
[sched] 榜单刷新完成：成功 6 / 失败 0 / 没跑完 1（lastupdate），耗时 25.01s
```

11-15 已经让「还欠哪一类」有名字（所以今天能秒读）。但**为什么会欠**没解决。
原注释写的是：

> 最坏 6 + 0.8 退避 + 6 = 12.8s < 25s，仍然回得来

这句话只算对了**一类**。一次全量刷新是 7 类、3 并发 → **3 批**：

```
3 批 × (6 + 0.8 + 6) = 38.4s  ≫  25s 预算
```

同机逐类实测（今天，正常网络）：

| 类目 | 耗时 | 条数 |
|---|---|---|
| allvisit | 1.88s | 30 |
| weekvisit | 1.81s | 30 |
| allvote | 2.73s | 30 |
| goodnum | 0.60s | 30 |
| monthvisit | 0.25s | 30 |
| postdate | 0.77s | 30 |
| lastupdate | 3.83s | 30 |

7 类串起来 11.87s，**每类都拿满 30 条** —— 说明 22:47 那次不是"站慢"，
是"重试一次"把两批各拖长了 6.8s。

修法：`RANKS_FETCH_RETRIES = 0`（原来 `retries=1`）。
最坏 3 × 6 = 18s < 25s，账才真的平。
代价：单源一次抖动就少它这一类的贡献（30 分钟后下一轮还在）；
收益：不会因为一个源抖动让**另一整类榜单停更一轮**。后者更贵。

判据是**结构性**的（只比常量关系，不碰耗时，耗时随机器负载漂）：

```
批数 × 单类最坏 ≤ 整轮预算
ceil(7/3) × 6.0 × (0+1) = 18.0s ≤ 25.0s
```

⚠ 判据盯的是**实参**（`current_retries()` 抓 `_fetch_source` 真传下去的值），
不是模块常量 —— 只断言常量的话，把调用点写成 `retries=1`（常量仍是 0）
就能绕过全部判据。
