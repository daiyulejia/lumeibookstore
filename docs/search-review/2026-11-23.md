## 二、主线缺陷：同一个页面/目录被并发抓 N 遍（同一条母题的第三次）

### 怎么发现的

线上日志看不见（没有流量），但 11-22 的欠账②写得很具体：

> `/api/preview` 一次慢到 **107s**（复测 1.5s）。根因是它与同 URL 的搜索在分页上竞态，
> 外层 `fast_mode` 不改变缓存 key，缓存命中也重解析。

拿两个线程直接打 `discovery.page_of()`（把 `webfetch.analyze` 换成记账的慢桩）：

```
analyze 调用次数 = 2 [('http://example.test/book/1/', True), (...True)]
结论 = 重复抓取（缺陷存在）
```

同一个地址、同一个模式，**两遍完整解析**。长书一次解析 = 21 页分页（每页 0.3~1.1s），
两份就是 42 页 —— 107 秒不是"慢"，是**重复**。

### 根因

**缓存只在"跑完之后"才有值。** 冷缓存下一瞬间来 N 个同一个 key 的请求，
N 个全部 miss、N 个都去干同一件事 —— 缓存挡不住这种重复。

两个入口，同一句话：

| 入口 | 现状 | 下面挂的活 |
|---|---|---|
| `discovery.page_of()` | 无合并 | 整页解析 + 分页目录（`full=True` 最多 40 页/25s） |
| `utils.cached()` | 无合并 | **7 个调用点**：configured / kunnu8×2 / template_source / wikisource / wyshu / xbqg5200，全是目录级 |

这是同一条母题的**第三次**：

1. **11-01** 16 个同名搜索各起一轮引擎 → 搜索引擎被我们打成"不认识这个词"，
   并发 8 个时 7/8 拿 0 条，单独搜是 2 条 → 已修（`searchflight.py`）。
2. **11-22** 长书两份完整分页（107 秒），而日志一直写 `候选=1 成书=1` 全绿。
3. **今天** `page_of` / `cached` —— 前两次修的都是"搜索入口"和"分页内部"，
   **没问一句：还有谁在重复干同一件事？**

### 修法

`app/utils.py` 新增 `single_flight(key, producer, ...)`（**不是在飞缓存**）：

- 领跑者跑，其余挂上去等同一份结果；**跑完就摘牌** —— 下一次调用照样重跑。
- 领跑者失败：等着的人**自己重跑一遍**，不集体继承失败（一次抖动不该按并发人数放大）。
- 领跑者卡死超过 `FLIGHT_WAIT=60s`：等待者自己跑（宁可重复一次也不把请求挂死 ——
  107 秒正是这个形状）。
- 同一线程递归重入同一个 key：直接自己跑（不能自己等自己）。
- 记账 `flight_stats{started,joined,timeout}` + 合并时打一行带 key 的日志
  （"用户能感知的差异，日志里必须有字段"）。

接入两处：

- `cached()` → `val = single_flight(key, producer)`；顺带把缓存时间改成**完成时刻**
  （原来记开始时刻：producer 跑 20 秒、TTL 30 秒时，结果刚放进去就已过期一半）。
- `page_of()` → key = `pg{0|1}:{url}`。**`full` 必须进 key**：探测只要 3 页、
  下载要 40 页，合成一份要么让下载拿到残目录，要么让探测陪着跑 25 秒。

## 三、副线：反证工具把今天的改动**静默回滚**了（当场被吃掉一次）

跑第一条突变时，`tools/mutate.py` 提示：

```
⚠ 捡到一个过期锁（1365 分钟前），当残留处理
⚠ 上一次没跑完，源码里还留着突变 —— 已还原：app\discovery.py
?  [单飞] 基线就是红的，跳过：...（6 条全跳过）
```

真相是：昨天 ship 被强杀时留下 `mutate_pending.json`，里面存着**昨天那版** `discovery.py` 原文。
今天启动时它照着昨天的原文回写 → **今天新加的 `single_flight` 整段消失**，
而工具只打一行「已还原」，接着的报错是"基线就是红的，跳过"（读起来像测试烂了）。

修：`_recover_pending()` 加时效闸门 —— 超过 `_RECOVER_FRESH=60 分钟`的残留
**只点名、不回写**（崩掉的那一轮几分钟内就会被发现；一小时前的残留说明
工作区大概率已经往前走了）。

判据（`tools/test_ship_chain.py` 新增 3 条，含自建临时文件）：
新鲜的残留要回写 / **过期的残留不许回写** / 清单要被清掉。

## 四、判据与反证

新增 `tools/test_page_flight.py`（19 条，已登记 `tools/ship.py` 的 `STATIC_SUITES`）：

```
A  cached() 并发未命中只跑一遍 producer / 两边同对象 / 跑完摘牌 / TTL 命中不调
A2 领跑者抛错 → 等着的那路自己重跑并拿到结果（只多跑一遍）
B  page_of 同址同模式只解析一次 / full 不同各解析一次 / 结果进缓存
C  领跑者卡住 → 等待者自己跑（并记账） / 同线程重入不死锁
D  flight_stats.joined 有数 / 合并时打日志带 key
E  结构闸门（AST）：cached() 与 page_of() 的函数体里必须有 single_flight 调用，
   且扫描器先自证"确实扫到了这两个函数"（否则判据恒真）
```

反证（`tools/mutate.py` 新组 `单飞` 6 条 + `残留` 1 条，**7/7 全抓**、源码逐字节还原）：

```
cached() 不走单飞                 → 两线程跑了 2 遍
登记簿永远当「没人跑」             → 两线程跑了 2 遍
page_of 的 key 里没有 full        → full=False/True 被合成一份
跑完不摘牌（退化成缓存）           → 下一次调用只跑了 1 遍（不再重跑）
领跑失败后不唤醒                  → 等待线程卡死（stuck=1）
缓存时间记成开始时刻               → TTL 等于没缓存（跑了 2 遍）
过期残留照样回写                  → 今天的内容被回滚成"昨天的原文"
```

### 反证过程本身抓到两条"没牙"的判据（值得记）

第一遍跑出来 3 条**存活**，都是判据自己的毛病：

1. 「跑完摘牌」原来在主线程连调两次 —— 单飞把**同线程重入**当"自己人直接跑"（防死锁），
   所以突变照绿。改成**换一个线程**再调。
2. 「两种预算不合并」和「领跑失败要唤醒」都缺**同步点**：两路可能天然错开
   （第一路早跑完了），突变就抓不到。改成让桩等到"真有人并进来"才继续（等**状态**，不等时长）。
3. `残留` 那条突变的锚点命中 2 处 —— mutate.py 自己也会被"唯一命中"扫描扫到，
   整句写进去等于命中"定义 + 清单"。改用拼串构造锚点。
