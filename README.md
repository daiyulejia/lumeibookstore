# 噜妹书院 · lumei novel dock

输入书名 → 自动搜索多个来源 → **去噪排序** → **探测哪些真的能打开** → 预览确认 → 下载成 txt。
部署在本机，同一局域网内任何设备都能通过浏览器使用。

界面是一套"噜妹"主题：粉奶油配色 + 圆脸吉祥物 + 漂浮的小脑袋背景，
外加「黑糖噜妹」深色版。品牌层集中在 `app/static/css/lumei.css`，
不想要整套皮肤直接删这个文件和 `index.html` 里对应的一行就回到中性外观。

## 快速开始

```bash
cd novel-downloader

# 首次：建虚拟环境 + 装依赖
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt      # Windows
# source .venv/bin/activate && pip install -r requirements.txt   # macOS/Linux

# 启动
.venv\Scripts\python run.py                        # Windows
# .venv/bin/python run.py                          # macOS/Linux
```

Windows 也可直接双击 `start.bat`。

### 人在外地、不在电脑边，怎么让它一直开着

这是最容易被忽略的场景：`start.bat` 是**前台**跑的，
**终端窗口一关服务就没了** —— 而你人在外面，根本看不到那个窗口。

正确用法是让它在后台静默跑（无窗口、脱离终端）：

```bash
python tools/service.py start     # 现在就在后台起来（崩了会自己重启）
python tools/service.py status    # 看状态（在跑吗 / 端口通吗 / 日志在哪）
python tools/service.py stop      # 停掉
python tools/service.py install   # 装开机自启，并立刻后台启动
```

`start` 的原理是 `pythonw.exe`（本身无控制台）+ `DETACHED_PROCESS`
（脱离父进程）—— 关掉终端、注销重登都不影响它。

> 顺带一个踩过的坑：**不要用 `wscript` 跑 `.vbs` 来启动**。
> 实测在受限环境里 `wscript.exe <vbs>` 会被安全策略拦掉，
> 而且**进程建了就消失、还不报错**，排查起来很费劲。
> `pythonw` 直接起静默程度一样，环节更少。
>
> `.vbs` 仍然会写进启动文件夹 —— 那是给「开机自动」用的，
> 和「现在就启动」是两件事。

启动后终端会打印：

```
本机访问 : http://127.0.0.1:8000
手机访问 : http://192.168.x.x:8000
           （手机连同一个 WiFi，浏览器输这个地址）
```

> 手机能不能连，取决于防火墙放行了没。启动器会**自己检查**，
> 必要时**自动借用一个已放行的解释器**来跑 —— 通常不需要你做任何事。
> 详见下一节。

## 手机上打不开？先看防火墙

这是本项目唯一一个「失败时**没有任何提示**」的坑，所以单独说。

手机连不上，九成不是服务的问题，而是 **Windows 防火墙把入站请求丢了**。
症状很误导人：电脑上 `127.0.0.1:8000` 一切正常，手机上就一直转圈。

更要命的是，防火墙里那条名叫「Python」的放行规则**多半没用** ——
Windows 的程序规则是**按 exe 路径**绑定的，它指向的可能
是别的 Python（比如某个 IDE 自带的），而不是本项目 venv 里的
`.venv\Scripts\python.exe`。这两个是不同的可执行文件。

### 但其实你多半什么都不用做

`run.py` 启动时会先自己查一遍防火墙。如果**当前解释器**不在白名单里，
它会去找一个**已经被放行**的 Python，直接借来跑：

```
⇄ 当前解释器不在防火墙白名单里，改用已放行的解释器启动
   D:\...\vendor\python\python.exe
   （命中规则「Python」，Python 3.13，无需管理员权限、不修改系统设置）
```

这不是什么技巧，而是顺着 Windows 的规则走 —— 防火墙按 exe 路径放行，
那就换个路径正确的 exe 来跑。**不改系统设置、不弹 UAC、不重启**。

借用有三个前提，不满足就自动退回普通启动（并在横幅里提示怎么手动放行）：

1. 那个 Python 的**大版本一致**（本项目 3.13 → 3.13，保证 ABI 兼容，
   能直接加载 `.venv` 里的依赖；小版本不同没关系）
2. 它的放行规则**覆盖了 8000 端口**（任何端口 / 列表里含 8000 / 区间含 8000）
3. 脚本会真的**跑一次 `--version` 确认版本**才敢借，不靠路径猜

想强制用当前解释器（比如就想验证放行规则本身）加 `--no-borrow`：

```bash
.venv\Scripts\python.exe run.py --no-borrow
```

### 想一劳永逸：按端口放行

**双击 `open-firewall.bat`**，它会自己申请管理员权限，
只放行这一个入站端口（不动防火墙总开关），跑完还会复验一次。
好处是**跟解释器无关** —— 以后换 venv、换 Python 版本都不用再管。

命令行版本：

```bash
.venv\Scripts\python.exe tools\firewall.py              # 体检：地址 + 放行状态
.venv\Scripts\python.exe tools\firewall.py --open       # 放行（需管理员）
```

不想用脚本的话，**以管理员身份**打开 PowerShell / cmd 粘这一行也行：

```cmd
netsh advfirewall firewall add rule name="NovelDock 8000" dir=in action=allow protocol=TCP localport=8000
```

界面上也能看：顶栏 📱 按钮会给出完整地址（带复制按钮）+ 防火墙状态。
`GET /api/net` 是同一份数据。

排查顺序：

1. 手机和电脑是不是**同一个 WiFi**（不是手机流量）
2. 电脑上这个程序还在跑吗（终端窗口关了就断了）
3. 防火墙放行了没（上面那步）
4. 路由器有没有开「AP 隔离 / 客户端隔离」—— 开了的话同一 WiFi 也互相看不见

> 手机不在同一网络（比如用 4G）时，局域网地址是够不着的，
> 需要内网穿透，见下一节。

## 部署到云服务器（腾讯云 / 阿里云 / 任意 VPS）

内网穿透是「临时借用一条通道」，好处是零配置，代价是地址每次都变、
免费隧道会慢。如果你有一台云服务器，把它部署上去是**更稳的长期方案**：
一个固定 IP，7x24 常驻，不依赖你家里那台电脑开着。

下面是**从买机器到手机能用**的完整流程。没碰过 Linux 命令行也能照着走完。

### 第一步：买机器时怎么选

| 选项 | 选什么 | 为什么 |
|---|---|---|
| **镜像** | **Ubuntu Server 22.04 LTS 64位**（公共镜像） | 见下面的说明 |
| **实例规格** | 2核2G 起步 | 够用。这个服务是单进程、几乎不吃 CPU，内存才是瓶颈 |
| **系统盘** | 40G 起 | 项目 30M + 依赖 200M + 日志和书架，20G 也够但别卡着边 |
| **带宽** | 3M 够用 | 看小说是文本，只有首次下发静态资源时略慢 |
| **安全组** | **放行 TCP 8000** | ⚠ 这一步最容易忘，漏了手机就是打不开 |

**镜像为什么选 Ubuntu 22.04 LTS 而不是别的：**

- ✅ **Ubuntu Server 22.04 LTS** —— 长期支持（到 2027），
  自带 `python3.10`，装 `python3-venv` 就是一行 apt。
  网上教程绝大多数也是 Ubuntu 的，你遇到问题好搜。
- ❌ **CentOS** —— CentOS 8 已经停止维护（EOL），
  7 也早就 EOL 了。包源都关了不少，新手最容易在这里翻车。
- ❌ **宝塔 / 应用镜像** —— 那是给你装 WordPress 用的，
  它自带的 Nginx 会**占用 80 端口并接管 Web 请求**，
  反而给这个纯 IP 直连的服务添乱。用**纯净的公共镜像**。
- ❌ **Windows Server** —— 2G 内存跑 Windows 本身就吃力，
  而且我们本来就有 Windows 那套（启动文件夹自启），没必要上云。
- ❌ **Debian 12** —— 其实也很好，但如果你手上有 Ubuntu 就选 Ubuntu，
  文档和社区答案更多。

### 第二步：一键部署（不用敲命令）

**最省事的做法是用界面上的按钮。** 打开程序 → 顶栏 📡「在别的设备上打开」→
拉到最下面「或者：部署到云服务器」那一块 → 点「复制」。

它会给你一条**已经填好你本机地址和令牌**的命令，形如：

```bash
curl -fsSL http://192.168.x.x:8000/api/deploy/sh?t=xxxx | bash
```

然后：买好服务器 → 在云控制台点「登录 / 网页终端」→ **粘这一条** → 等 2~3 分钟。
装完脚本会自己判断通没通，直接打印出手机该打开的地址。

> ⚠ **注意这条命令只在「服务器能连到你的电脑」时才成立。**
> 如果服务器在公网、你的电脑在家里的内网（`192.168.x.x`），
> 服务器**连不上**那个地址，会卡到 `Connection timed out`。
> 这是实测踩过的坑，判断方法：你电脑的地址是不是 `192.168.*` / `10.*`？
> 是的话走下面「手动做法」里的 `scp`，方向反过来（你推上去）。

**手动做法**（等价，而且**在云服务器场景下才是正确的那个**）：

```bash
# 1) 本机打包（自动排除 .venv / *.exe / 截图，147M → 9.4M）
python tools/pack.py --out dist/noveldock.tar.gz

# 2) 传上去。注意用户是 ubuntu 不是 root ——
#    腾讯云轻量默认建的用户就是 ubuntu，root 登录会被拒
scp dist/noveldock.tar.gz ubuntu@<公网IP>:~/

# 3) 登上去，解压，一键装
ssh ubuntu@<公网IP>
tar xzf noveldock.tar.gz && cd noveldock
bash tools/oneclick.sh
```

> Windows 上更省事：双击项目根目录的 **`部署到云服务器.bat`**。
> 它会自动打包、问你公网 IP、然后把上面两条命令**拼好给你复制**。

> **忘了放行安全组？** 脚本会在最后**替你测一次外网通不通**（从服务器回连
> 自己的公网 IP，走的是外网路径），测出来没通就直接告诉你「去安全组放行
> TCP 8000」，并把放行后的完整地址一起给你。不用你自己判断。

### 关于这几个部署接口的安全性

`/api/deploy/*` 是新加的，守法和别的接口不一样，值得说清：

| 接口 | 谁能取 | 为什么这么设计 |
|---|---|---|
| `/api/deploy/sh` | 任何人 | 它只是「怎么装」的说明书，不含任何数据；服务器在装上之前也拿不到令牌 |
| `/api/deploy/guide` | 任何人 | 同上，就是把 README 部署那节渲染成网页 |
| `/api/deploy/tar` | **只有局域网直连** | 这个包里**含访问令牌**（`cache/auth.json`）。所以守的是「来源」，不是令牌 —— 从隧道进来的请求**即使带着正确令牌也一律 403**，不能让它把整个项目连钥匙一起拉走 |
| `/api/deploy` | 局域网 / 带令牌 | 返回那条安装命令；**只有本机请求**才在命令里带令牌 |

关键点：`tar` 的守卫用的是 `security.is_local()`（来源判据），
**不是**令牌判据 —— 因为取包的那台服务器还没装上服务，不可能有令牌；
反过来，隧道请求就算有令牌也不该给。这两件事是正交的，用令牌管反而管错了对象。

### 第三步：2G 内存必须配 swap（脚本已代劳）

2G 内存跑 pip 安装、之后常驻服务，可能在某个瞬间打满内存，
然后被内核的 OOM killer **直接杀掉进程** —— 表现是「服务莫名其妙就没了」，
而且日志里看不出原因。加 2G swap 是这台机器上性价比最高的一步。

`setup_linux.sh` 会检查并自动创建 `/swapfile`（写进 `/etc/fstab`，重启后仍有效）。
已经有 swap 就跳过。

### 第四步：让它常驻（systemd）

Linux 上没有 Windows 那种「启动文件夹」，正确的做法是 **systemd**。
`tools/service.py` 会自动识别系统 —— 在 Linux 上走 `systemd --user`，
命令和 Windows 一模一样：

```bash
.venv/bin/python3 tools/service.py install   # 装自启 + 立刻启动
.venv/bin/python3 tools/service.py status    # 看状态 + 地址 + 令牌
.venv/bin/python3 tools/service.py stop      # 停
.venv/bin/python3 tools/service.py remove    # 卸掉
journalctl --user -u noveldock -f            # 实时看日志
```

**用了 `--user`（不是系统级 unit）**，所以不需要 sudo，
而且服务的数据（书架、令牌）都在你自己的 home 目录里，属主天然正确。

> ⚠ **最关键、最容易漏的一步：`loginctl enable-linger`。**
>
> user 级服务默认**只在你登录期间**运行 —— 你是 ssh 进去的，
> 一断连 systemd 就把 session 收走，服务跟着停。表现出来就是
> 「装好了、跑着、我关掉 ssh、去手机上打不开」。
>
> `install` 里会自动尝试执行 `sudo loginctl enable-linger $USER`。
> 如果没配好免密 sudo，它会打印一行提示让你手动执行 —— **照做**。

### 第五步：安全

直接用 `http://<公网IP>:8000` 访问，意味着这个端口**对整个互联网敞开**。
项目自带的那层防护因此不是可选项，而是必须的：

- **`/api/*` 全部要求令牌**（经代理进来、或服务绑在 `0.0.0.0` 时从非回环
  地址进来的请求）。
  猜不到的：令牌是 `secrets.token_urlsafe(18)`，约 144 bit 随机量。
- **判据不只看代理头**。这一点是踩过坑改的：只看 `CF-Connecting-IP` /
  `X-Forwarded-For` 的话，**云服务器直连（浏览器直接打 IP，没有代理头）
  会被误判成局域网直连而放行**。所以现在的判据是：
  > 带代理头 **或**（绑定 `0.0.0.0` **且** 来源非回环）→ 判为公网入口，要令牌
- **静态资源不设防**（页面骨架、CSS/JS）—— 因为它们不含数据，
  而浏览器请求它们时不会带 `?t=`，拦了就是白屏。
- **SSRF 防护**：`/api/adapt` 是「你给网址、服务端去抓」，
  公网入口一开它就是个现成的内网探测跳板。抓之前先解析域名，
  内网 / 回环 / 云元数据（`169.254.169.254`）一律拒绝。
- **限流**：公网入口按来源 IP 限速（10 秒 / 150 次）。

所以：**别把带令牌的链接发到公开的地方**。令牌等于钥匙，
换令牌只能用本机 `POST /api/auth/rotate`。

> 想更稳一点：绑定域名 + 上 HTTPS（Caddy 自动签证书），
> 或者干脆只开放内网、用云厂商的 VPN。这里选的是**最简单的直接 IP 访问**，
> 所以令牌那层一定要留着。

### 以后改了代码，怎么同步上去（`tools/sync_cloud.py`）

第一次部署走 `oneclick.sh` 就够了。**之后每次改完想更新线上**，
不要再手工 `scp` + `tar` + 挑文件覆盖 —— 那条路我走过三次，
有一次差点把服务器的 `library/` 覆盖掉（读过的进度全没）。

```bat
:: 本机，项目根目录
.venv\Scripts\python tools\sync_cloud.py
```

一条命令做完全部五步：

| 本机步骤 | 做什么 |
|---|---|
| 1/5 打包 | 调 `tools/pack.py`，排除 `.venv` / 截图 / 字节码（147M → 12M） |
| 2/5 上传 | `scp` 到 `~/noveldock_new.tar.gz` |
| 3/5 远端升级 | 解压后**只覆盖代码**，数据目录一概不碰（见下表） |
| 4/5 验证 | 打 `/api/health` 与 `/api/library`，逐本打印书名/章节/状态 + 首页标题 |
| 5/5 完成 | 打印带令牌的访问地址 |

服务器内部还会做七件事（编号在本机侧看不到，日志里标成 `[服务器 N/7]`）：
① 备份当前代码 → ② 覆盖代码 → ③ 补 `cache/` 里缺的键 → ④ `app/*.py` 语法自检
→ ⑤ **书架体检** → ⑥ 重启服务 → ⑦ **清理本次残留**（删掉 13M 的解压目录与上传包，
并只保留最近 3 个代码备份，避免改十次堆十个）。

**保留 vs 覆盖**（这是这个脚本存在的全部理由）：

| 服务器上 | 处理 |
|---|---|
| `library/` `downloads/` `logs/` `.venv/` | **完全保留**，不碰 |
| `cache/*.json`（令牌、榜单、来源库、书源索引） | 缺的补上，**已有的保留服务器版本** |
| `app/` `tools/` `run.py` `requirements.txt` `probe.py` `README.md` `*.bat` `*.sh` | 覆盖成本机版本 |

**书架体检**会自动把「有 `ch/` 但没有 `meta.json`」的孤儿目录隔离出去。
这类目录是下载中断留下的残骸，健康接口不数它们，但会一直躺在 `library/` 里，
造成「页面上书架说 4 本、`ls library` 却有 5 个目录」这种对不上的怪象。
被隔离的目录挪到 `~/noveldock.orphan-quarantine/`，**不删除**，随时能捞回来。
`status: toc` 的书（只抓了目录 + 前几章，用户正在读的）**一律保留**，绝不清理。

**自动清理**（步骤 7/7）保证服务器不会被自己的备份撑爆：
删除本次解压目录与上传包（各 13M），代码备份只留最近 3 个。
**不会碰** `noveldock.bak-1011-2303` —— 那是唯一带完整 `library` + `downloads` 的
86M 备份，真正的回滚基准。

其它开关：

```bat
.venv\Scripts\python tools\sync_cloud.py --dry-run     :: 只打印要做的事
.venv\Scripts\python tools\sync_cloud.py --skip-pack   :: 复用 dist/noveldock.tar.gz
.venv\Scripts\python tools\sync_cloud.py --skip-verify :: 跳过线上验证
```

服务器地址可用环境变量覆盖，不必改脚本：
`NOVELDOCK_HOST`（默认 `106.53.203.108`）、`NOVELDOCK_USER`（`ubuntu`）、
`NOVELDOCK_KEY`（`~/.ssh/noveldock_ed25519`）、`NOVELDOCK_PORT`（`8000`）、
`NOVELDOCK_TOKEN`。

> 包里带着 `cache/auth.json` 和 `远程访问.txt`，也就是**访问令牌**。
> 这是刻意的（全搬过去，手机不用重配），代价是**这个 tar.gz 本身是敏感文件**：
> 别发到公开地方，传完可以删。

```

```

  （这才是大多数人真正的问题）

### 「我有链接，但钥匙呢」—— 这个死循环专门堵了一下

公网进来的请求要带**访问令牌**（`/api/*` 无令牌一律 401；
只有页面骨架和静态资源是公开的，不然没地方输入令牌）。
于是有个很现实的坑：**令牌只有在已经进去之后才看得到**，
而进去的前提就是有令牌。人在外面、只有一台手机的时候，谁也救不了。

实测就是这么卡的 —— 手机里存着一条裸地址 `https://xxx.trycloudflare.com`，
打开就是「需要访问令牌」，而那串 key 在电脑上，人不在电脑边。

四处一起兜：

- 顶栏「网络」面板里能直接复制令牌，也能一键复制**带令牌的完整链接**
- 隧道一拿到公网地址，就把**当前这条能直接打开的完整链接 + 令牌**
  写进程序目录的 `远程访问.txt`（换地址、关隧道、换令牌都会跟着更新）
- 启动横幅（电脑上的那个窗口）直接打印 `访问令牌` 和 `远程访问` 两行 ——
  这窗口只在本机屏幕上，写在里头没有额外暴露面
- 「需要访问令牌」那一页把「去哪找」三条路一次说清，
  并提醒**那条链接本身就带了钥匙、收藏整条就够了**

顺带说清两件容易搞混的事：**令牌不会自己变**（只有点「换一个令牌」才变，
换完所有旧链接立刻失效）；**手机和电脑连同一个 WiFi 时走局域网直连，根本不用令牌**。

## 长期挂在后台

`run.py` 是前台进程：终端一关、或某次未捕获异常把进程带走，服务就没了 ——
而你可能正在外面用手机看小说。让它在后台长期跑、崩了自己起来：

```bash
python tools/service.py status    # 看状态
python tools/service.py install   # 装开机自启 + 立刻在后台启动
python tools/service.py remove    # 取消自启并停止
```

自启用的是**启动文件夹里的一个 `.vbs`**，不是 Windows 服务、也不是计划任务 ——
后两者都要管理员权限，而启动文件夹是纯用户级的，重启电脑后自己就在了；
`.vbs` 还能完全静默（不闪黑窗口）。

守护逻辑在 `tools/serve.py`：

- **崩了自动拉起**，带指数退避（3s 起步、最长 60s），不会疯狂重启刷日志
- **日志按天切**到 `logs/server-YYYY-MM-DD.log`，自动清理 7 天前的
- **单实例**：已经在跑就不再起第二个（否则会抢端口和缓存目录）
- 调用子进程时**强制用项目 `.venv` 的解释器**，不认 `sys.executable` ——
  否则被别的 python 拉起时，`import uvicorn` 会失败、秒退、然后被无限重启

## 安全：令牌 + SSRF + 限流

接上公网之后，「没有鉴权」等于把书架、导出文件、删除接口一起送人。
这一层在 `app/security.py`。

**访问令牌**

- 经代理进来的请求（隧道 / 反代）必须带对令牌，否则 401
- **局域网直连不拦** —— 那是你自己的网，加锁只会让人烦。
  判据是请求里有没有 `CF-Connecting-IP` / `X-Forwarded-For` 这类代理痕迹
- 存在 `cache/auth.json`，可用环境变量 `NOVELDOCK_TOKEN` 覆盖
- 怀疑链接被转发时换一个：`POST /api/auth/rotate`。**换令牌只能在本机操作**
- 令牌明文也**只发给本机**：`/api/net` 是给「电脑上看地址、复制到手机」用的，
  同一 WiFi 的别的设备调它只会拿到前 4 位提示

**为什么页面和静态资源不设防**：浏览器请求 `<link>` / `<script>` / `<img>`
这些子资源时**不会**带上 `?t=` 参数。如果连它们一起拦，公网打开就是
「HTML 401 + CSS/JS 也 401」= 一片白屏，穿透功能直接废掉。
而它们本身不含数据，敏感信息全在 `/api/*` —— 守住那些就够了。

**SSRF 防护**：`POST /api/adapt` 是「你给个网址，服务端去抓」，
公网入口一开它就是个现成的内网探测跳板。所以抓之前先解析域名，
内网 / 回环 / 链路本地 / 云元数据（169.254.169.254）一律拒绝。
关键是**解析出真实 IP 再判** —— 只判字符串会被 `127.0.0.1.nip.io`
这种「解析到 127.0.0.1 的域名」绕过。

**限流**：公网入口按来源 IP 限速（10 秒 / 150 次），防的是令牌到了别人手里
被拿去狂刷；局域网不限。

## 功能

**搜索阶段**

- **多源并行搜索**：所有来源同时查，结果边搜边显示
- **相关性去噪排序**（`app/relevance.py`）：
  解决「搜《微微一笑很倾城》却搜出 `北京互联网法院（2021）京0491民初9699号民事判决书`」这类问题。
  判定原则是——对「找一本书」来说，**标题匹配才是有效信号，正文命中是噪音**。
  打分维度：标题精确匹配 > 包含 > 模糊相似；再对判决书 / 论文 / 章节页 / 话题模板类标题重罚。
  繁简自动统一（`zhconv`），所以搜「红楼梦」能正确匹配维基文库的「紅樓夢」。
- **自适应门槛**：找到高分结果时只保留同一档次的候选（宁缺毋滥）；
  确实没有像样结果时才放低门槛兜底。
- **「确切命中」判定**（`relevance.tightness`）：
  分数挡得住判决书，挡不住**撞词**——搜《活着》，新笔趣阁会返回
  「原神：活着」「我怎么还活着」「生活不止是活着」，都是真书、分数都不低，
  但没有一本是余华那本。判据是「关键词在标题里占得多满」：
  容差 = 关键词长度的 1/3（至少 1 字），并先剥掉尾部的「（全集）」「（顾漫 著）」。
  有确切命中时就不端沾边的上来；一条都没有时，前端会挂一条
  「**没找到确切的《X》**，下面 N 本只是沾边」的横幅，而不是装作用户搜到了。
- **候选可用性探测**：搜索完立刻并发打开每个候选的目录页，标出
  `✓ 可用 · 51 章` / `✕ 打不开`，可用的自动排到最前面。
  同时把目录缓存下来，点下载时不用再抓一遍。
- **两级深度校验**：目录能打开 ≠ 正文能看（有的站正文要登录，有的站被限流后
  返回一页广告）。所以还要**抽第 2 章真读一下**，检查长度、汉字占比、
  登录页特征、导航混入。而且**没抽过就不许说可读** —— 没做这一步的候选
  显示「目录 N 章 · 正文未验证」，不给绿标。详见下面「可读性」。
- **够用就停**：验出 4 个可用候选 / 3 本正文本就提前收手，不再等剩下的。

## 搜索为什么快 / 曾经的「一直显示正在从 N 个来源里找」

搜索是**并行扇出** 6 个来源然后合并排序的。最初的实现用
`for fut in as_completed(futs)` 等**全部**来源返回，于是总耗时 = 最慢那个来源的耗时。
而最慢的那个往往**一条结果都贡献不了**（实测搜《活着》时 wyshu 花了 14.5s、
贡献 0 条）—— 用户就这么盯着「正在找…」干等。

现在的策略是分层的（都在 `app/engine.py` 顶部有常量）：

| 常量 | 作用 |
|---|---|
| `SEARCH_MIN_WAIT` | 至少等这么久，免得第一个快源刚回来就收摊 |
| `SEARCH_GRACE` | 已有结果 + 至少两个源答过 → 再宽限这么久就收手 |
| `SEARCH_SOFT_DEADLINE` | 已有结果时的墙钟上限 |
| `SEARCH_ENOUGH` | 攒够这么多原始候选就收手 |
| `SEARCH_ANSWERED_RATIO` | 已有结果 + 这么多比例的源答完就收手 |
| `SEARCH_HARD_DEADLINE` | **一条结果都还没有**时的上限，到点才放弃 |

关键点：**「有结果」的判据是"真的推给前端过"（`streamed`），不是 `len(raw)`**。
原始候选可能全是噪声（实测搜「诡秘之主」raw=20 条、去噪后 0 条），
拿 raw 当判据会「1.8 秒收手、返回空」——比慢更糟。

### 三个踩过的坑（都是"看起来对、实际完全没生效"型）

这三种错法有一个共同点：**不报错、不崩、日志正常**，只有盯住耗时才发现没用。

1. **`as_completed` 是阻塞的**。写成
   `for fut in as_completed(futs): ...判断 elapsed 再 break`
   看着有墙钟，其实**一批源集体慢的时候循环体一次都不执行**，
   那个 6 秒上限形同虚设。必须给 `as_completed` 传 `timeout`。

2. **`list(as_completed(pending, timeout=w))` 不是「回一个处理一个」**。
   它会**阻塞到全部完成或超时**，一次性把整批塞给你。实测 6 个源在第一次调用
   里就被全部收走、循环体只跑一轮 —— 收手判断永远来不及执行。
   正确做法是 `next(as_completed(...))`，一次只拿一个。

3. **`streamed` 的累加不能写在 `if on_result:` 里**。
   不传回调时（比如引擎被直接调用）它就恒为 0，「已有结果」永远不成立，
   于是所有搜索都跑满全部源 —— 提速改动等于没写。

- **来源库**：联网发现的战果会攒起来（站点的目录模板 / 正文容器名 + 书的地址和章数），
  搜过的书下次秒出；界面里可以「体检」和「清失效」。详见下面「来源库」。
- **来源健康检查**：一键并发 ping 所有来源首页，汇总「几个正常 / 几个打不开」，

  （快站绿、慢站黄）。小说站域名寿命很短，隔三差五查一下。
- **深链**（刷新保持状态 / 能直接发给别人）：
  `#search=书名`、`#shelf`、`#files`、`#read=书架id`，
  以及来源抽屉的 `#sources`（实时检测）和 `#registry`（来源库）。
- **域名冷却**：被限流后短时间内直接快速失败，不反复死磕同一个站。
- **字体反爬破解**：新笔趣阁用 PUA 码位（U+E800~）把章节名渲染成乱码，

**阅读阶段（本地书架）**

- **书落盘就秒开**：一本书一个目录（`meta.json` / `toc.json` / `ch/00001.json`），
  一章一个文件（1500 章的书不能塞进一个 JSON），写入用「临时文件 + `os.replace`」保证原子性。
  读过的书**离线也能看**，不用再抓网页。
- **正文收口统一处理**（`base.tidy_content`）：清站方模板行 + 去开头重复的标题。
  小说站几乎都会把章节标题渲染两遍（一次在 `<h1>`，一次作为正文第一行），
  照原样读出来每章都从标题开始、还要再念一遍「点此举报」。
  去标题用**互相包含**判定而非完全相等（有的站正文首行只是标题的后半截），
  并且**循环剥**（有三体站点两种写法都写了一遍）。所有落地路径
  （阅读 / 缓存 / 导出）都走同一个函数，避免漏掉一处。
- **阅读器缓存优先**：命中缓存直接返回；没命中的章节联网补一章并回写缓存，
  同时后台预取后面 3 章（in-flight 去重，快速翻页不会重复请求）。
- **产品级阅读器**：目录抽屉（可搜索、标出已缓存）、上一章/下一章、
  **上一页/下一页（分栏翻页）**、顶部进度条 + 可拖拽跳章、
  5 套主题（日间 / 羊皮纸 / 护眼绿 / 夜间 / 纯黑）、
  字号 / 行距 / 字体 / 版心宽度、滚动与翻页双模式、沉浸模式、
  快捷键（`←` `→` 翻页，`空格` 下翻，`[` `]` 换章，`T` 主题，`S` 设置，`F` 沉浸，`Esc` 退出）、
  自动记忆阅读进度。

**导出阶段**

- **多格式**（`app/exporter.py`）：TXT / **EPUB 3** / **单文件 HTML 阅读版**。
  EPUB 是手写的最小实现（只用 `zipfile` + XML，不依赖任何第三方库），
  含 `container.xml` / `content.opf` / `nav.xhtml` / `toc.ncx` / 分章 xhtml + 样式表。
  HTML 版本身就是一个带目录抽屉、上下章、主题切换、进度条、快捷键的小阅读器，
  发给别人直接双击就能看。
- **取消下载**：下载中可以随时中断（`stop` 回调贯穿整个抓取循环）
- **熔断保护**：连续多章抓不到正文就判定来源挂掉并报错，
  而不是傻乎乎跑完全部请求、最后交给你一个空文件
- **章节数限制**：可选只下前 N 章（长篇小说试跑很有用）
- **失败自动降级**：某源抓不全时自动换下一个候选
- **任务抽屉**：所有导出任务带进度条，刷新页面后也能恢复

### 动态站点池：为什么要有自动适配

内置来源永远是有限的，而且笔趣阁系域名平均寿命只有几个月 —— 今天写死的类，
明天就 404。用户搜不到某本书时，最可能的答案不是「这本书不存在」，
而是「我们没接那个站」。所以与其一个个手写适配器，不如做**结构推导**：

```bash
# 扫一批候选域名，看哪些还活着、哪些还能搜
python tools/probe_pool.py --search 斗破苍穹

# 对活着的站批量跑「搜索 → 目录 → 正文 → 质量校验」，通过才落盘
python tools/adapt_pool.py --keyword 活着
```

界面上就是顶栏那个 🔌 按钮：粘一个网址进去，它真的跑一遍
「打开首页 → 找搜索接口 → 推导搜索条目 → 推导目录 → 推导正文」，
每一步都显示出来，最后用 `check_content_quality()` 判定抓到的正文是不是真的
（不是登录页 / 广告 / 导航）。**推不出合格正文就直说卡在哪，不生成
「看着像但抓不到东西」的配置** —— 那比没有更糟。

推导策略不是硬编码选择器，而是**候选模式库 + 实测打分**：

- 先认站点指纹（wordpress / empirecms / dedecms / thinkphp / generic）
- 搜索接口：扫首页表单和常见路径模板，GET/POST 都试；实测「关键词真的出现在结果页」才算可用
  （否则「参数不生效直接返回首页」会被误判成搜索成功）
- 搜索条目 / 目录：多个通用 `<a>` 提取模式，看哪个捞出的「像书名的链接」最多；
  再用 **URL 形状聚类**（`/12/12454/93000.html` → `/#/#/#.html`）甩掉
  logo / 导航 / 侧边栏
- 正文：候选容器模式 + 「汉字密度」兜底，扫全部容器类型（div/section/article/td/main），
  按「汉字数 × 汉字占比」挑正文，再照它的 id/class **反推成可复用的正则**
  —— 只把这段文字抠出来不算成功，得能逐章复用

一条容易踩的坑：适配时用 URL 形状过滤甩掉了导航，**运行时必须做同样的事**。
所以 `ConfiguredSource._clean_list()` 会重跑一遍同样的过滤，保证「推导」和
「运行」一致，否则那套正则落到运行时会把整页链接都当成章节。

### 联网发现：本地全搜不到，就自己出去找

自动适配解决的是「**你手动粘一个 URL**，我来推配置」。还有更常见的一种情况：
你根本不知道该粘哪个 URL —— 这本书在百度上明明一搜就有，本地来源却一条都没有。

所以加了第三条路：**本地来源全军覆没时，自己出去找**。

```
本地 6 个来源都打不开或没这本
        ↓
① 搜索引擎找书页          app/websearch.py
   Bing 给真实 URL（<h2><a href>）；百度给 mu 属性里的真实地址
        ↓
② 并发核实每个候选        app/webfetch.py
   直链打开 → 自己看出目录在哪、正文在哪 → 不像目录的直接扔掉
        ↓
③ 记进来源库              app/registry.py
   站点的目录模板 / 正文容器名、书的地址和章数都存下来
```

**关键洞察：绕开站内搜索。** 实测 `www.29zw.com` 的 `/search.php` 被 Cloudflare
拦得死死的（403），但它的详情页 / 目录 / 正文全敞开 —— 它不是不能抓，只是不能搜。
而「搜」这件事搜索引擎已经替我们做了，所以这条链路根本不需要那些站的搜索功能，
也就绕开了最容易被封的一环。

**解析靠通用启发式，不写死任何站点的规则**（`app/webfetch.py`）：

- **目录**：把所有 `<a href>` 归一化成模板（数字 → `#`）后分组，章节链接必然
  「同一模板、几百上千条」，导航链接只有个位数。但光分组还不够 ——
  实测 29zw 的详情页顶部挂着「最新章节」面板（9 条、倒序），下面才是完整目录
  （4534 条、正序），**两者 URL 模板一模一样**，直接读出来就是
  `第1559章 末章` → `第4553章` → `第4552章` → … → `第一卷第一章`。
  所以还要靠 **URL 里哪一列数字在变**认出章节号并重排 —— 这一列就是章节号，
  比猜「第几个数字是 id」稳得多，也适用于 `/book/1234/5678.html` 这种多段路径。
- **不像目录就扔掉**（`toc_quality`）：判据是「URL 数字列单调」+「标题里带
  『第N章/节/回/卷』的比例」。只看条目数会选中「猜你喜欢」——实测塔读的详情页
  就栽在这儿，抓回 1561 条「章节」，第一条叫《药鼎仙途》。
- **正文**：优先用**上次在这个站学到的容器名**（存在来源库里），否则扫常见命名
  （`htmlContent` / `content` / `chaptercontent`…），再兜底按「文本密度」找。
  抓不到合格正文就当失败 —— 塔读这类正版站目录静态可读、正文要 JS 渲染，
  绝不能标成「可读」让用户点进去看一屏 UI 骨架。

**用起来是这样的**（界面上直接能看到过程）：

```
  · 联网搜索       本地没有《万古神帝》，出去找找
  · Bing 搜到结果   7 条
  · 百度 搜到结果   7 条
  · 核实候选站点    12 个地址
  · 发现可用来源    万古神帝 · 5011 章 (www.bqgbi.net)
  · 发现可用来源    万古神帝 · 4233 章 (www.hongxiu.com)
  · 发现可用来源    万古神帝 · 78 章 (m.qidian.com)
  · 来源库已更新    新收录 7 条
```

触发条件刻意保守：**只有在「什么都没搜到」或「搜到的全打不开」时才联网**。
本地能出结果就绝不联网 —— 联网是兜底，不是常规路径。联网发现来源是 `lazy` 的，
不参与每轮搜索的并发扇出，否则每搜一次都要多跑两个搜索引擎。

### 粘一个地址直接抓

「我在百度上搜到了这本书的页面，地址在这儿」—— 那就别再让它搜了。
搜索框里粘的是网址时，按钮会变成「直接抓这个地址」，走 `POST /api/fetch-url`：

```bash
curl -X POST http://127.0.0.1:8000/api/fetch-url \
     -H "Content-Type: application/json" \
     -d '{"url":"https://www.29zw.com/info_68516/"}'
# → {"ok":true,"kind":"toc","title":"药鼎仙途","author":"寒香寂寞","chapters":4543,
#    "sample":{"sampled":true,"readable":true,"chars":960,"note":""}}
```

和搜索共用**同一套**通用启发式（`app/webfetch.py`），所以口径完全一致。
认完目录会**再抽一章验一下正文**，实测：

| 地址 | 结果 |
|---|---|
| `https://www.29zw.com/info_68516/` | 4543 章，抽样 960 字 → **读得到** |
| `https://www.tadu.com/book/x/349017/toc` | 1561 章，抽样 495 字但是控件页 → **正文抓不到** |

不验的话付费站会显示成「目录可达」，点进去一个字都没有 —— 那条红线还在。
深链也支持地址：`#search=https://…` 刷新能保持、能直接发给人。

### 热门榜单：不知道看什么的时候，先看别人在看什么

发现页往下滚就是「🔥 热门榜单」。它抓的是第三方站的**公开榜单页**，
不是我们自己的统计 —— 所以榜单上的书和书架没关系，纯粹是「外面在流行什么」。

后端 `app/ranks.py`，两个接口：

```bash
curl "http://127.0.0.1:8000/api/ranks/kinds"
# → {"ok":true,"kinds":[{"kind":"allvisit","label":"总点击榜","desc":"历来被点开最多的"}, …]}

curl "http://127.0.0.1:8000/api/ranks?kind=allvisit"
# → {"ok":true,"kind":"allvisit","label":"总点击榜","count":20,
#    "items":[{"title":"赵氏嫡女","author":"粽爷萌萌哒","url":"https://www.384g.com/html/195/195679/",
#              "words":"1057824字","updated":"2023-09-10","status":"连载中"}, …]}
```

**为什么是这 6 类**（`allvisit` / `allvote` / `goodnum` / `size` / `postdate` / `lastupdate`）——
只列**实测真的有内容**的。384g 上还有 `monthvisit`（月点击）、`weekvisit`（周点击），
但抓下来是**站点自己的空表**（4838 字符 vs 正常 11451），所以没放进目录，
免得用户点进去看到一个空框还以为坏了。

**怎么确认它是真榜单、不是一张表换个名字**：实测三类榜首**完全不同** ——

| 榜单 | 榜首 |
|---|---|
| 总点击榜 | 赵氏嫡女 |
| 总推荐榜 | 僵尸帝王 |
| 总收藏榜 | 东北往事：黑道风云20年系列（共7册） |

要是三个都一样，那就是同一张表贴了三个标签，没意义。

**认列靠位置，不靠猜内容**。表格列序是 `书名｜最新章节｜作者｜字数｜更新｜状态`，
但「最新章节」那格**偶尔会缺**，所以不能死认下标。做法是先把「字数 / 日期 / 状态」
这几格按形状挑出来（`\d+字`、`\d{4}-\d{2}-\d{2}`、`连载中|已完结`，形状唯一不会误判），
剩下的按原顺序排，**跳过书名后的第 2 个**才是作者。

早先试过"按内容启发式认作者"，踩了个坑：把「最新章节」那格的 `新书来了~` 认成了作者
（它太短、又不带「第..章」形状，启发式拦不住）。改成按位置后加了回归断言：
**「插翅难飞」的作者必须是「风动铃心」**（`tools/test_ranks.py`）。

#### 定时刷新：三层保险，让榜单永远是热的

榜单**不能等用户点的时候才去抓** —— 那意味着每次冷启都要先盯着「正在加载」
等 3~4 秒联网。所以做了三层，周期全部对齐 **1800 秒（30 分钟）**：

| 层 | 是什么 | 什么时候起作用 |
|---|---|---|
| ① **落盘缓存** | `cache/ranks.json` | 进程重启后立刻有内容，不用等联网 |
| ② **进程内调度器** `app/sched.py` | 一个后台线程，每 30 分钟 `refresh()` | 服务活着的时候 |
| ③ **systemd timer** | `noveldock-ranks.timer` | 服务根本没起来时的系统层兜底 |

**为什么必须三层**：只有 ② 的话，服务崩了没人刷；只有 ③ 的话，两次 timer
之间进程重启，缓存就是空的。三者周期**刻意对齐** —— 如果 ② 说 30 分钟、
① 说 10 分钟，那缓存会在两次刷新之间过期，用户正好撞上"现抓"的那一次。

**⚠️ 落盘读回时不能重置时间戳。** `_load_from_disk()` 刻意保留**原抓取时刻**：
如果读回来就写"刚刚抓的"，那份陈旧数据会骗用户整整 30 分钟（它明明已经过期，
却对外宣称 fresh）。`tools/test_sched.py` 的 A 段专门断言这一点。

**⚠️ `refresh()` 内部吞异常 → `last_error` 会假空。** `ranks.refresh()` 把
单类异常计数进 `failed` 而不往上抛，所以 `sched.run_once()` **永远不会进 except**。
结果是运维看到「跑过了、错误字段空着」，而实际上 6 类可能全挂了。所以必须
**主动把「全灭」翻译成 `last_error`**。这是实测踩出来的，`test_sched.py` 断言锁住。

**⚠️ 定时任务必须打接口，不能另起进程 `import`。** 另起进程抓会写同一个
`cache/ranks.json`，但**跑着的服务内存里还是旧的** —— 等于白刷一轮，而且抓取
逻辑会分裂成两份。`tools/ranks_cron.py` 的做法是 `POST /api/ranks/refresh`。

**运维入口**：

```bash
# 看一眼缓存和调度器的体检报告
curl -H "X-Token: <你的令牌>" "http://127.0.0.1:8000/api/ranks/status"
# → {"ok":true,"cache":{"kinds":{"allvisit":{"count":20,"age":24,"fresh":true,…}},
#                       "stale_count":0,"oldest_age":26,"total":120},
#    "sched":{"enabled":true,"running":true,"interval":1800,"last_error":""}}

# 立刻手动刷一次（force=true 无视 TTL 重抓）
curl -X POST "http://127.0.0.1:8000/api/ranks/refresh?kind=allvisit"

# systemd timer
systemctl --user list-timers noveldock-ranks --no-pager   # 下次什么时候刷
systemctl --user start noveldock-ranks.service            # 手动跑一次
journalctl --user -u noveldock-ranks -n 50 --no-pager     # 看执行日志
```

装/卸定时任务的命令（Linux）：

```bash
.venv/bin/python3 tools/service.py install-ranks --port 8000
.venv/bin/python3 tools/service.py status-ranks
.venv/bin/python3 tools/service.py remove-ranks
```

Windows 上**不需要装**（`service.py` 会明确提示）：进程内调度器已经在跑，
而 Windows 没有 systemd 这一层概念，第三层用不上。

**关掉定时刷新**：`NOVEL_SCHED=0`（或 `run.py --no-sched`）。间隔可用
`NOVEL_SCHED_INTERVAL`（秒）调，首次延迟用 `NOVEL_SCHED_FIRST_DELAY`。

**❗ systemd timer 三要素**（少一个就会在某个场景静默失效）：

- `OnCalendar=*-*-* *:00/30:00` —— 周期
- `OnBootSec=3min` —— 开机后 3 分钟补跑一次
- `Persistent=true` —— 补跑错过的时点（关机期间跨过的那些）

另外 oneshot service **不该带 `[Install]`** —— 带了 systemd 会把它当成
可 enable 的常驻服务，语义就错了。`test_service_unit.py` 里有断言锁住。

**❗ 模板文件必须从真实项目目录读。** `_render_tmpl()` 一度用 `svc.ROOT`
去读 `.tmpl`，而 `ROOT` 会被测试替换成假路径（用来验渲染结果），于是那次
查找就变成 `PurePosixPath('/home/ubuntu/…').read_text()` → 直接崩。
改成 `Path(__file__).resolve().parent` 后正常。

**榜单上的脏数据故意不清洗。** 384g 的 size 榜里，有些书名**尾部粘着作者名**
（例如 `茶鸢厉九泽`，作者字段里也有「厉九泽」）。这不是我们的解析 bug，是源站
自己的脏数据。**故意原样透出**：第 3 行标题 `茶鸢厉九泽` 如果把笔名剪掉反而更错
（真书名到底叫 `茶鸢` 还是 `茶鸢厉九泽`，源站自己都没说清）。`test_ranks.py`
G 段同时锁住两件事：脏数据原样透出 **且** 干净书名「永生诀」没被误伤。


**缓存 30 分钟，且空结果不覆盖好缓存。** 榜单是爬别人站的页面，没必要每次都去敲；
但更关键的是：站点偶尔抽风返回空表时，**不能把上次抓到的 20 条冲掉**：

```python
items = _fetch_one(kind)
if items:                      # 只在真拿到东西时才写缓存
    _CACHE[kind] = (time.time(), items)
```

多个榜单并发抓时只开 **3 个线程** —— 一共就 6 个请求，而且 `utils` 里有同域限速，
开更多只会一起排队，反而更容易触发对方风控。

> ⚠ **榜单数据是"照抄"第三方站点的**，所以站方写歪的字我们原样透出。
> 实测 `size` 榜头几行，站方把笔名拼进了书名链接里（`乡下千金她又掉马甲了茶鸢`，
> 而旁边作者格写的是「孙宝珠」）。这是**源站数据脏，不是解析 bug** ——
> `title` 取的就是那个 `<a>` 的文字。这里**故意不做清洗**：
> 第 3 行标题叫 `茶鸢厉九泽`（笔名+男主名），剪掉笔名反而更错；
> 任何按字符匹配的剪法都会误伤名字里恰好含这几个字的正常书。
> 回归里把这个决定钉住了（`== G. size 榜…脏数据（原样透出）==`）。

**榜单条目点了会怎样**：不是新开页面，而是**复用搜索流程** ——
把书名填进搜索框 → 面板自动收起（不挡结果）→ 开搜。
也就是说榜单是「发现入口」，点下去还是走那套「联网搜索 → 逐本验证真有正文」，
不会凭空给你一个没验证过的下载。这个行为有 12 项真浏览器断言守着
（`tools/test_ranks_ui.py`，用 CDP 点真的按钮看会发生什么）。

榜单样本固化在 `tools/fixtures/`（`384g_allvisit.html` / `384g_size.html` /
`384g_empty.html` / `luoxiaks_top.html`），所以解析是**离线可回归**的：
站点改版导致解析失效时，`test_ranks.py` 会变红，能第一时间发现。
备选源 `luoxiaks.net`（UTF-8，384g 是 GBK）也留了样本。

### 来源库：越用越大 —— 而且会**自己学会站内搜索**

联网找到的站和书都记在 `cache/registry.json`：

```json
{
  "sites": {
    "www.384g.com": {
      "name": "新笔趣阁",                            // 学到的站名（给人看的）
      "toc_tpl": "www.384g.com/html/#/#/#.html",    // 学到的目录模板
      "content_hint": "content",                     // 学到的正文容器名
      "search_tpl": "/search.php",                   // ★ 学到的站内搜索地址
      "search_method": "post",                       // ★ 是 GET 还是 POST
      "search_body": {"s": "{kw}"},                  // ★ POST 时关键词放哪
      "search_enc": "utf-8",                         // ★ 关键词用哪种编码
      "search_scheme": "https",
      "ok": 6, "fail": 0, "last_ok": 1760000000
    }
  },
  "books": {
    "https://www.384g.com/html/186/186246/": {
      "title": "药鼎仙途", "author": "寒香寂寞",
      "host": "www.384g.com", "chapters": 1604, "ok": 3
    }
  }
}
```

#### 两段路：从「先搜才有站」到「先有站直接搜」

来源库原本只是**书籍级缓存** —— 记着「哪本书在哪个 URL」。所以搜过《药鼎仙途》
之后，同一个站里的**另一本书仍然搜不到**：库里没它的地址，而这个站的搜索接口
我们没记。换一本书就得重新出去走一趟搜索引擎。

现在补上了缺的那环 —— **站点级可搜源**：

```
第一本《药鼎仙途》 →  本地 7 个预置源都没有 → 联网发现 → 找到 A / B / C 站
                     → 顺手学会 A / B / C 的站内搜索接口 → 存进来源库
第二本《另一本》   →  本地预置源没有 → RegistrySource 直接拿关键词问 A / B / C
                     （不用再走搜索引擎！）→ 1 秒内出结果
```

用到的两个模块：

| 模块 | 干什么 |
|---|---|
| `app/sitelearn.py` | **学**：从一个站的首页反推它的搜索接口（form / JS / 链接 / 爆破 + 验证） |
| `app/sources/registry_source.py` | **用**：拿关键词直接搜所有「学过搜索接口」的站，参与常规扇出 |

#### 怎么学会一个站的搜索接口

按证据强度从高到低试，命中即止：

1. **HTML 的 `<form>`** —— 站内搜索框本来就是给用户填关键词的，`action` + `input[name]`
   就是现成答案。GET 直接拼查询串；**POST 也支持**（实测 384g 就是 `POST /search.php  s=…`）。
2. **外部 JS 文件** —— ⚠ 这里踩过一个大坑：很多中文小说站（尤其杰奇 CMS 系的
   老站）的搜索框不是写在 HTML 里的，而是脚本 `document.writeln` 出来的：

   ```js
   function searchBox(){document.writeln(
     "<form action='/modules/article/search.php' target='_blank'>…
      <input type='text' … name='searchkey'>…</form>");}
   ```

   静态 HTML 里**根本没有 form**，只从 HTML 里找永远找不到（实测 29zw 就是这样）。
   所以要再去读站点的 JS 文件，从里面挖 `action=` + `name=`。
3. **首页的搜索链接** —— 有些站搜索是 GET 链接而不是 form（`<a href="/s?q=都市">`），
   把示例关键词换成 `{kw}` 就是模板。
4. **爆破常见路径** —— 上面都没找到才用：`/search.php?q=`、`/search?keyword=`、
   `/modules/article/search.php?searchkey=`（杰奇 CMS 系经典）、`/plus/search.php`（帝国 CMS）…
   一共几十种组合，逐个发请求验证。

**验证**是必须的：拿一个已知书名去请求，**回内容里有一堆章节链接才算成**
（用 `webfetch.extract_toc` 数）。判据不能是「页面里有没有关键词」——
很多站搜不到时会回首页，首页当然有链接，只数关键词会把它误判成成功。
另外还要探**编码**：中文老站大量是 GBK 的，关键词编码错了站方就搜不到、返回空，
所以 UTF-8 试不通会再试 GB18030。

学不出来的站会记一笔 `search_fail`，累计 3 次就不再浪费预算去爆破
（同一批站里总有几个真的没有站内搜索，比如纯静态站，或者在 Cloudflare 后面的）。

#### 一段实测记录

```
[来源库体检] 开始 —— 站 37（可搜 1） / 书 19
[来源库体检] 完成 —— 查了 19 本，存活 18 · 失效 1，清理 0 本 / 4 站
[来源库体检] 学接口完成 —— 新学会 1 个站（失败 2 / 跳过 0），现在共有 2 个可搜源
[来源库体检] 结果 —— 站 37→33（可搜 1→2） / 书 19→19
```

学到的两个源（下一轮搜索就能直接用）：

```
www.384g.com   POST  /search.php          body={'s': '{kw}'}
www.tadu.com   POST  /search            body={'query': '{kw}'}
```

搜一本**全新的**书（没走过搜索引擎）：

```
《三体》    → 6 条  0.9s      《活着》 → 6 条  0.5s
《诡秘之主》 → 6 条  0.5s      《斗破苍穹》→ 6 条  1.2s
```

对比：走一遍联网发现要**十几秒**。这就是「搜得越多，能搜的源就越多」的实际收益。

#### 攒下来有四个直接收益

1. **下次搜同一本书秒出** —— 不用再走一遍搜索引擎和十几个站的核实，
   首屏 `来源库命中 N 本` 就是它
2. **★ 拿任意关键词直接搜已学会的站** —— 这是「L 源自我壮大」的核心：
   每联网发现一次，就多几个可搜源，下次搜**别的**书也能用上
3. **同一个站第二次抓直接用上次学到的模板和容器名** —— 不再重新猜；
   站名也顺手学会了（从 `og:site_name` 或 `<title>` 的尾巴上认出来），
   界面上显示「落霞读书」而不是 `www.luoxiaks.net`
4. **能做健康筛选** —— 界面「来源」抽屉 → 「来源库」页签里有「体检」和「清失效」；
   体检会把记下的书重开一遍（只确认目录页能不能打开、章数还对不对，不抓正文），
   连续打不开的自动清掉

#### 深夜自动体检

体检要打几十个请求，白天跑会和用户抢带宽。所以线上由 **systemd timer**
在**凌晨 3:17 / 3:37 / 3:57** 各跑一轮（没人用的点）：

```bash
python3 tools/service.py install-registry     # 装（幂等）
systemctl --user list-timers noveldock-registry --no-pager   # 下次什么时候跑
systemctl --user start noveldock-registry.service            # 立刻体检一次
journalctl --user -u noveldock-registry -n 50 --no-pager     # 看执行日志
```

一晚跑 3 轮而不是 1 轮是刻意的：第一轮常碰到站点抽风（临时 502 / 超时），
多跑两轮能把它救回来，避免「偶然一次打不开就被清掉」。
执行体是 `tools/registry_nightly.py` —— 和 `ranks_cron.py` 一个道理，
它**走接口**而不是自己 import：服务本体才有来源库的内存缓存，
另起进程体检写的是同一个 `registry.json`，但跑着的服务看不到，用户界面上没变化。

一条踩过的坑：来源库是**进程内缓存 + 退出时落盘**的。如果第二个进程也动过这个文件，
直接覆盖会把它写进去的东西整片抹掉 —— 实测一个只读过空库的进程退出时，
把攒了几十站的库清成了空文件。所以 `_save()` 会**先把磁盘上的那份读回来做合并**
（键取并集，同键比时间戳），删除则单独记墓碑。

**测试自己也踩过同一个坑，而且更狠**：`tools/test_registry.py` 最早是直接读写
`cache/registry.json` 的（先备份、测完写回去）。看着没问题，实际上
`prune(only_dead=False)` 会把真库里每个键**记进墓碑**并立刻落盘 ——
备份救回了文件，救不回已经写下去的墓碑；再加上进程退出时 `atexit` 又 flush 一次，
跑一次测试就能把攒好的来源库洗成只剩测试夹具。现在三件事一起兜：

- 测试用 `NOVEL_REGISTRY` 环境变量把库指到临时目录，**全程不碰生产库**，
  并且把「生产库一个字节没变」当断言
- `prune(only_dead=False)`（唯一的「一次调用清空全库」入口）**必须显式传 `confirm=True`**，
  默认参数越危险越要让人打出来
- `_save()` 前有**缩水护栏**：盘上至少 5 条、且新内容不到一半时，先留一份
  `registry.bak.json`。正常清失效是逐条删的，不会一次砍掉一半以上 ——
  真出现这种量级，多半是事故，留一份底能把不可逆变成可逆

### 可读性：没验证过的不许给绿标

「目录能打开」和「正文真能读」是两件事。正版站（塔读、起点这类）经常是这个形状：
目录页静态可读、正文页也能打开，但正文要登录或 JS 渲染 ——
抽出来的就全是**控件文字**（登录 / 打赏 / 投票 / 字体大小 / 页面宽度），
一行几个字，总量还不算少。实测塔读某章抽出 **61 行 / 440 字，平均每行 7 个字，
一个字正文都没有** —— 而老的质量判据只看「够不够 120 字」，它轻松过关。

拦这类页面得看**形状**而不是长度（`webfetch.looks_like_ui_skeleton`）：

- 命中的 UI 词种类 ≥ 5 **并且** 平均每行字数 < 14，两条同时成立才判死。
  只用一条都不够：真实章节里出现「登录」两个字很正常，
  短章的平均行字数也可能偏低。

还有一处更隐蔽的：`readable` 原来写成 `available and sample_ok is not False`，
意思是**「没抽样」被当成了「可读」**。而抽样为了省时间有「同一来源最多抽两本」
的规则，联网发现偏偏是一个来源底下挂着几十个站 —— 5 个不同站点被当成同一个来源、
只抽了 2 个，剩下 3 个没抽过的就顶着「可读」出现，点进去一个字都没有。
两处一起改：

- 抽样配额**按「来源 + 域名」计数**（内置来源一个来源就是一个站，行为不变）
- `BookResult.readable` 改成**要正面证据**：抽过且正常才算可读；
  没抽过一律不算（`sampled` 字段专门区分「没抽」和「抽了但没结论」，
  后者是维基文库 / Gutenberg 这种没有单章接口的来源）
- 前端跟着分三态：`✓ 可读` / `目录 N 章 · 正文未验证` / `✕ 打不开`，
  聚合层也把 `readable_count` 和 `available_count` 分开数

另外两个解析判据也顺手收紧了：

- **目录质量评分**：原来「URL 数字单调」就给 0.8 分，可「猜你喜欢」那一排
  `/book/1234/`、`/book/1235/` 的书 id 本来就是顺序发的、同样单调。
  现在要求标题里**至少有一条**像章节名，一条都没有的直接降到 0.35。
- **目录重排**：站点常把「最新章节」那一小块（倒序）和完整目录（正序）塞进同一组，
  URL 模板一模一样。原来靠「97% 有序才重排」，29zw 那本 4543 章能对
  （倒序的 9 条只占 0.2%），换成一本 60 章的书，同样 9 条倒序占 13%，
  判据立刻放弃排序 —— 用户看到的第一条变成「第60章 大结局」。
  现在拆成两个函数：`_monotonic`（97%，回答「像不像目录」）和
  `_sort_direction`（60%，回答「要不要重排」）。这条是小书用例逼出来的，
  `tools/test_parse.py` 里同时钉了 60 章和 40 章两档。


### 反爬：被封了别继续撞

实测 `www.29zw.com`：反复请求十几次之后，**连接直接超时**（连首页也一样，
`ConnectTimeout`），而同期百度 / 落霞 / 西红柿全部秒开 —— 这是连接级封禁，
不是站点挂了。

处理方式：

- **连接建不起来就当被封**（`utils.mark_blocked`），记 90 秒冷却。
  冷却期内对它的请求直接快速失败，不再白等一次超时 ——
  核实 12 个候选时，一个连不上的站重试一次就是 2 倍超时，会把整轮预算吃光。
- **核实阶段 `retries=0`**：硬性卡住时间上限，不让单个慢站拖垮整轮。
- **来源库里连续失败的站直接跳过**，不再为它占一个并发槽。
- 界面「来源」抽屉里会显示每个来源**此刻**能不能打开，并附一句提醒：
  小说站经常抽风 / 限流 / 换域名，打不开不代表永久失效。

### 章节分页：别让「下载成功」的书缺 2/3

一批笔趣阁模板把一章拆成几页（页内有 `第(1/3)页` 标记，链接是
`xxx.html` / `xxx_2.html` / `xxx_3.html`）。只抓第一页的话，
书看起来下载成功了，实际每章只有前 1/3，**而且用户完全看不出来**。

- 适配器探测到分页标记时，自动给配置写 `chapter_paged: true`
- 运行时 `ConfiguredSource.fetch_chapter()` 按 `page_url()` 推出后续页并拼接；
  下一页返回空或与上一页内容完全相同时停止（很多站页面不存在会把上一页原样返回）
- 实测：`斗破苍穹` 某章单页 4498 字 → 拼接后 12525 字（≈3 倍）

### 正文模板行清理

小说站的章节页几乎每章都挂着同一句站方模板，留着会让每一章都从一句广告开始：

```
『章节错误,点此举报』        ← 章首
…… 正文 ……
『加入书签，方便阅读』        ← 章尾
：。：                       ← 纯符号垃圾行
```

`base.strip_boilerplate()` 只删**整行判定命中**的，并且把关键词分两档 ——
「章节错误 / 点此举报 / 加入书签」这类足够特定，允许行内任意位置命中；
而「广告 / 声明 / 上一章」这类太泛，必须**开头 + 够短**才算 banner。
不然「他说：这本小说的广告打得真好。」这种正文会被整行吃掉，一章少一句，
用户根本不会发现。回归见 `tools/test_boiler.py`。

已经在书架里的旧章节不会自己变干净，跑一次 `python tools/retidy.py --apply` 即可。


### 无忧书城：搜索接口被封怎么办

`wyshu.com` 的搜索是 EmpireCMS 的 POST `/e/search/index.php`，直接请求返回 **403**。
解法是绕开搜索接口：

1. **爬分类页建本地索引** —— 站点把全部书按 `/{分类}/` 列出来（8 个分类约 800 本），
   抓一遍存到 `cache/wyshu_index.json`（24 小时过期），在索引里做子串匹配；
2. **拼音直拼兜底** —— 站点用拼音 slug 当书路径
   （微微一笑很倾城 → `/ys/weiweiyixiaohenqingcheng/`），索引里没有时用
   `pypinyin` 把书名转拼音直接拼 URL 试。

详情页有完整的 `og:novel:*` 元信息（book_name / author / category / latest_chapter），
比解析 HTML 里的书名可靠得多。

## 动效层：让"顺手"成为可检查的东西

动效的失败方式是**静默**的 —— `motion.css` 404 了、变量没解析、
过渡类忘了摘，这些都不会让任何功能坏掉，只是"界面变朴素了"，
一路带到线上也没人发现。所以它被拆成两层，且**两层都有测试**。

### 分了三层，各管各的

| 层 | 文件 | 管什么 |
|---|---|---|
| **动效**（中性） | `css/motion.css` | `--mo-*` 令牌、涟漪、错峰、入场、状态连续性 |
| **编排**（中性） | `js/motion.js` | 什么时候动：错峰注入、视口触发、主题过渡开关、滚动收缩 |
| **品牌**（噜妹专属） | `css/lumei.css` | 吉祥物浮动、极慢漂浮物、章末收尾标记 |

中性层**不含任何噜妹元素**。删掉 `motion.css` + `motion.js`，
站点会变朴素但不会坏 —— 这是"品牌可摘"之外的又一条可逆性保证。

### 三条纪律（写在 `motion.css` 顶部，改这个文件前先读）

1. **点到即反馈** —— 按压位移 ≤ 3px、时长 ≤ 170ms，
   涟漪挂在 `pointerdown` 上而不是 `click`：反馈必须跟上手指，不等网络。
2. **位移分层** —— 容器走 8px、主元素走 14px；背景动得慢、卡片动得快。
   全都走同一段距离就没有纵深，看起来像一整块被推上来。
3. **尊重 `prefers-reduced-motion`** —— CSS 和 JS 两侧都读。这是可访问性要求。

### 几个刻意的决定

**主题切换用"按需过渡"，不是全局常驻。**
给 `*` 挂常驻 `transition` 会让每一次重绘都走插值，滚动和翻页直接掉帧。
所以只在切换那一刻给 `<html>` 挂 `.mo-theming`，色值插值 280ms，切完立刻摘。

```js
withThemeTransition(() => applyTheme());   // 挂类 → 改主题 → 500ms 后摘类
```

**列表项按下时不缩放。**
整行缩放在视觉上像抖动。行元素（榜单、来源卡）改为压暗背景 ——
这更符合"列表项"的语义。

**加载态不用三点动画。**
三个跳动的圆点的问题不是丑，是**没有信息量**：用户不知道在等什么。
换成「噜噜在翻书」+ 一行说明，至少传达了两件事：在动、在找书。

**错误态用定格表情，不做浮动。**
「懵」这个情绪要传达的是"出了点问题"。让它上下浮动会显得"没事"。
**动效必须与语义一致**，不是为了好看就加。

**章末装饰必须用 CSS 背景，不能用 `<img>`。**
分页算法靠量每个段落的 `offsetTop` 切页，任何占高度的元素插进正文都会
把页码算错（表现为"最后一页还有半页空"或"某段被吞掉"）。背景图不参与布局。

## 全量按钮测试（`tools/test_buttons.py`）

`docs/button-checklist.md` 是一份人工清单（43 条），`tools/test_buttons.py` 是它的机器版：
CDP 起一个真 Chrome，按 A~F 六组把每个按钮都点一遍，**断言它真的发生了副作用**

```bash

tools/test_buttons.py --group D -v                        # 只跑阅读器那组
```

### 这一轮抓到的两个真实缺陷（不是测试问题，是产品 bug）

**1. 榜单里「去看我的书架」点了没反应。**
`ranks.js` 写的是 `location.hash = "#shelf"`，但页面只在**加载时**跑一次
`bootRoute()` 读 hash，**运行时改 hash 没有任何人听** —— 于是点了等于没点。
修法：`main.js` 里挂 `hashchange` 监听重跑路由，`shell.js` 的 `nav()`
也改成同步写 hash（用 `replaceState`，避免和监听器互相触发）。

**2. 用过一次「仿真翻页」再切回来，目录 / 上一章 / 下一章**全部**静默失效。**
这是最隐蔽的一个。`StPageFlip` 的 `destroy()` 会执行 `this.distElement.remove()`
—— **把它的宿主元素从 DOM 里删掉**，而我们传给它的宿主正是持久的 `#rdFlipBook`。
切过一次 flip 之后这个容器就没了，后续 `setStageBusy()` / `setStageHTML()` 里
设置 `innerHTML` 全部抛 `Cannot set properties of null`，而它是在 `await` 链里，
**异常被吞掉，界面上一点提示都没有**，用户看到的就是"这些按钮全坏了"。
修法：给 StPageFlip 一个**用完就扔的内部子节点**（`.flip-host`）当宿主，
`#rdFlipBook` 本身不动；同时给 `setStageHTML` / `setStageBusy` 加空值保护。
测试里留了 `D10b` 当回归锁：切过 flip 之后必须还能翻章。

> 顺带两个测试自身的坑，也记下来：测试里**不能假设打开阅读器就是第 1 章**
> （书架存了阅读进度，会从上次读到的章续读），所以 D 组开头先显式复位到第 1 章；
> 另外章节正文要联网抓，**固定 `sleep` 会偶发不够 → 假失败**，一律用轮询 `wait()`。

## 日志与埋点（`app/logging_setup.py`）

### 改造前的问题（有诊断数据）

线上一天的日志 **8210 行，其中 3850 行（47%）是 httpx 的爬取噪声**
（`HTTP Request: GET https://xxx 200 OK`）。而且 uvicorn 的访问日志**没有任何关联标识**：

```
22:31:04 INFO httpx: HTTP Request: GET https://a.com/1 "200 OK"   ← 噪声
22:31:04 INFO httpx: HTTP Request: GET https://b.com/2 "200 OK"   ← 噪声
22:31:05 INFO 127.0.0.1 "GET /api/search 200 OK"                   ← 没有 id
22:31:06 ERROR 入书架失败: 'NoneType' object has no attribute 'get' ← 属于哪次搜索？
```

结果是：**真出问题时根本串不起来**。

### 改造后：三条原则

**① 降噪** —— `httpx` / `httpcore` / `urllib3` / `uvicorn.access` 一律压到 WARNING
（保留 WARNING 是因为"请求失败"这类还是有价值的信号）。
实测一次搜索：原来几百行 → 现在 `app.log` 5 行，**全是有效信息**。

**② 串联** —— 每个请求一个 4 位 `req=` 短 id，一路传到线程池和后台任务里。

**③ 可筛** —— 事件名统一 `模块.动作`，能直接 grep：

```
03:15:28 [INFO] req=xlbt novel.app: search.start 书名=三体 指定来源=全部 抽样=True 探测=True 联网=False
03:15:28 [INFO] req=xlbt novel.app: http method=GET path=/api/search status=200 ms=3
03:15:30 [INFO] req=xlbt novel.engine: search.rank 关键词=三体 原始=60 去噪后=3
03:15:35 [INFO] req=xlbt novel.app: search.done 书名=三体 候选=3 成书=1 可读=3 耗时ms=6740
```

同一个请求的完整生命周期一眼看完。

### 两个容易踩的坑（都踩过）

- **ContextVar 不跨线程** —— `engine.search` 跑在 `run_in_executor` 的线程池里，
  不手动 `set_request_id()` 接过去的话，引擎打的日志全是 `req=----`，
  而**那段最需要追的过程反而没有 id**。
- **ContextVar 不跨任务** —— 缓存/导出是 `create_task` 起的后台任务，
  同理要手动接。现在两处都接了。

### 慢请求会自己浮出来

中间件对 `/api/*` 记 `ms=`，**超过 800ms 标"慢"**。
"为什么卡"是最高频的抱怨，有这一行就不用靠猜。

### 拉线上日志（`tools/logs.py`）

```bash
python tools/logs.py                      # 最近 100 行
python tools/logs.py --level ERROR        # 只看错误
python tools/logs.py --event search.fail  # 按事件名筛
```

### 日志文件

| 文件 | 内容 | 什么时候看 |
|---|---|---|
| `logs/app.log` | **结构化日志**，带 `req=` 和事件名 | 查业务问题（缺哪章、哪个源挂了） |
| `logs/app.log.YYYY-MM-DD` | 同上，按天轮转，保留 14 天 | 翻前几天的 |
| `logs/server-YYYY-MM-DD.log` | 守护进程重定向的**原始 stdout** | 查"进程起没起"，兜底 |

单文件超过 8M 也轮转 —— 免得一次大批量缓存把单个文件撑到几十 M，`tail` 都卡。

## 如何新增来源

**方式一：配置化（推荐，不改代码）**

编辑 `app/sources/sites.json`，按里面 `_字段说明` 和 `_示例` 加一条即可：

```json
{
  "name": "mysite",
  "display": "我的来源",
  "priority": 30,
  "enabled": true,
  "base_url": "https://www.example.com",
  "encoding": "gb18030",
  "search_url": "https://www.example.com/search.php?keyword={kw_gbk}",
  "search_item_re": "<a[^>]+href=\"(?P<url>/book/\\d+/)\"[^>]*>(?P<title>[^<]{2,40})</a>",
  "chapter_re": "<dd>\\s*<a[^>]+href=\"(?P<url>[^\"]+\\.html)\"[^>]*>(?P<title>[^<]+)</a>",
  "content_re": "<div[^>]+id=\"content\"[^>]*>(?P<c>[\\s\\S]*?)</div>",
  "book_title_re": "<h1[^>]*>([^<]+)</h1>"
}
```

**方式二：写类（需要多步解析时）**

- `app/sources/kunnu8.py` —— 「API 搜索 → 详情页解析 → 目录 → 正文」多步流程
- `app/sources/wyshu.py` —— 「搜索接口被封 → 爬分类页建本地索引 + 拼音直拼」

写完在 `app/sources/__init__.py` 注册即可。

```python
        if limit: chapters = chapters[:limit]
        book = Book(...)
        # fetch_all 帮你处理：中断检查 + 连续失败熔断
        book.chapters = self.fetch_all(chapters, self.fetch_chapter, progress, stop)
        return book
    def fetch_chapter(self, chapter) -> str: ...           # 预览和下载共用
```

`probe()` 有默认实现（= 试取目录，取到即判定可用）；单页来源（维基文库 / Gutenberg）覆写它。

## 环境变量

| 变量 | 默认 | 说明 |
|---|---|---|
| `NOVEL_MIN_INTERVAL` | `0.3` | 同一域名两次请求的最小间隔（秒），被限流时调大 |
| `NOVEL_USE_PROXY` | `0` | 设为 `1` 才走系统代理（默认忽略代理，避免境外站超时） |
| `NOVEL_SCHED` | `1` | 榜单定时刷新开关；设 `0` 关掉（等价于 `run.py --no-sched`） |
| `NOVEL_SCHED_INTERVAL` | `1800` | 榜单刷新间隔（秒），默认 30 分钟 |
| `NOVEL_SCHED_FIRST_DELAY` | `60` | 启动后首次刷新的延迟（秒） |
| `NOVEL_RANKS` | `cache/ranks.json` | 榜单落盘位置，换一份可以避免测试搅乱生产缓存 |

限流与退避策略：4xx 立刻放弃（不浪费重试）；连接被重置最多重试 1 次；
5xx / 429 / 超时按 0.8s → 1.6s → 3.2s 指数退避 + 随机抖动。

### 手机上点不动按钮 / 页面"卡住"上滑没反应

这两个症状（用户报过一次，实测复现并修掉）根因是三件独立的事，都会撞在一起：

**1. 按钮太小，手指点不中。**

`.btn.sm` 在桌面上的实测高度只有 **32.6px**，而结果卡片里那个「↧ 导出」
按钮（`.btn.sm.icon`，只有一个字符）只有 **26.6×32.6px** ——
面积不到 iOS 建议的 1/4。手指点下去大概率落在按钮外面，
体感就是"点了没反应"。

修法是加一整块 `@media (hover:none), (pointer:coarse)`：

```css
.book .acts .btn{padding:11px 18px;font-size:14.5px;min-height:44px}
.book .acts .btn.icon{padding:11px 16px;min-width:44px}
```

修后实测 **96×47 / 79×47 / 48×47**，全部达标。两个查询用逗号并列命中：
`hover:none` 管"没有悬停能力"，`pointer:coarse` 管"指针很粗"（手指），
任一成立就按触摸处理 —— 比单用一个保险。

**2. iOS 会粘住 `:hover`，卡片"浮起来下不去"。**

`.book:hover{transform:translateY(-3px)}` 在桌面上是个好效果，
在 iPhone 上点一下卡片会**保留 hover 态直到点别处** —— 用户看到的就是
"点完卡住了"。所以触摸块里要把位移型的 hover 全关掉：

```css
@media (hover:none), (pointer:coarse){
  .book:hover{transform:none}
  .btn:hover{transform:none}
  .rd-btn:hover{background:transparent}
  .btn:active{transform:scale(.97)}   /* 按下反馈交给 :active，抬手自动消失 */
}
```

**3. 300ms 双击缩放延迟。**

没声明 `touch-action` 时，Safari 会把第一次点按拿去判断"是不是双击缩放"，
于是第一次点看起来没反应。给所有可点元素加：

```css
.btn,.chip,.tabbar button,.srow .mini{touch-action:manipulation}
```

### 还有一个"卡住"的真凶：`body` 滚动锁没被放开

进阅读器时锁住背景页滚动（`body{overflow:hidden}`），退出时放开。
原来的代码在 `catch` 里**只渲染错误文案、没解锁** ——
而打开失败恰恰是服务挂了时必然发生的事。结果就是：**锁上、报错、永远解不开**，
整个页面滚不动、手指上滑没反应。

现在改成两道保险：

```js
function lockScroll(on){ document.body.style.overflow = on ? "hidden" : ""; ... }
function unlockScrollGuard(){ document.body.style.overflow = ""; }
// 打开失败 → unlockScrollGuard()；closeReader → unlockScrollGuard()
// 外加 3 秒兜底：如果阅读器已经不在前台了，自动把锁摘掉
```

### 怎么测这些

桌面 Chrome 里 `(hover:none)` **恒为 false** —— 直接在桌面视口测触摸样式
等于什么都没测。`tools/shot.py` 于是加了 `--mobile`：

```bash
python tools/shot.py <url> out.png --w 393 --h 852 --mobile
```

它会设 `mobile:true` + `setTouchEmulationEnabled` + `deviceScaleFactor=3`，
让触摸媒体查询真正命中。

还有 `--js`：页面加载完、截图之前跑一段 JS，把界面点到要截的状态。
`--pre` 是在页面脚本**之前**跑的（用来预置 localStorage），改不到 DOM、
点不了按钮 —— 要截「点开某个抽屉之后」的样子得用 `--js`：

```bash
python tools/shot.py http://127.0.0.1:8000/ net.png --w 900 --h 1500 \
  --wait '#btnNet' --ms 8000 --settle 3500 \
  --js "document.querySelector('#btnNet').click()"
```

（`--settle` 要给足，抽屉里的内容是异步拉回来的，点完立刻截只会拍到骨架屏。）

`tools/test_reader_ui.py` 里对应加了 7 项断言，并在 iPhone 尺寸 + 触摸模拟下跑：
媒体查询是否命中、三个按钮热区是否 ≥42px、「↧」宽度是否 ≥40px、
`.book` 的 hover 位移是否已关、末卡按钮底边是否还在底栏上沿之上。

门槛取 42 而不是 44 是有意的：修复前 32.6px、修复后 47px，42 卡在中间，
能把"触摸优化被改回去了"一刀切出来 —— 设 44 会放过 43px 这种"差不多但没做"。

**反向验证过**：把触摸块故意写坏（`(hover:none) and (pointer:fine)`），
3 项热区断言立刻报错（`78×35` / `63×35` / `35×35`），
说明这些断言真的有辨别力，不是橡皮图章。

## 注意事项

- 服务监听 `0.0.0.0`，同一局域网可访问。要给外网用请走界面上的**内网穿透**
  （自带访问令牌那一层），**不要**自己在路由器上把端口映射出去 —— 那样是裸奔
- Windows 首次运行可能弹防火墙提示，需允许"专用网络"
- 仅供个人学习研究，请遵守目标站点 robots 规则与著作权规定
- 第三方源会失效，这是常态；用界面上的「来源检测」看谁还活着，
  用 `probe.py` 找新源，或改 `sites.json`
- **别拿同一个站猛测**：实测 `www.29zw.com` 被连着请求十几次之后，
  连接直接超时（连首页都打不开）—— 这是连接级封禁，解封要等。
  正常使用不会这样（一次搜索对同一个站最多请求 2 次），
  但调试抓取逻辑时记得别死磕同一个域名
- 来源库（`cache/registry.json`）是联网发现的战果，删了不影响使用，
  只是下次搜同一本书要重新走一遍搜索引擎

### 联网发现为什么是「兜底」而不是「默认」

它的代价很实在：一次要跑两个搜索引擎 + 并发核实十几个站点，大约 10 秒起。
而本地来源（写了适配器的站）通常 3~5 秒就出结果。所以：

- 本地**只要有能打开的结果**，就绝不联网
- 联网发现来源标了 `lazy`，不参与每轮搜索的并发扇出
- 搜过的书进来源库，下次命中就直接用，不再联网

想在界面上手动触发也很简单：搜索框上方的**来源筛选条**里只勾「维基文库」这类
本来就不会有这本书的来源，它立刻就会转去联网；或者干脆清空筛选让它自然兜底。

### 改了前端却没生效？多半是浏览器缓存

页面 `GET /` 带 `Cache-Control: no-cache` + `ETag`，静态资源引用带
`?v=<最新 mtime>`（见 `app/main.py` 的 `_asset_version()`）——
所以正常情况下改完刷新就能看到。

**但这次改造恰好踩过这个坑**：之前 `GET /` 什么缓存头都没有，
浏览器按「没有缓存头」的启发式规则自作主张缓存了整页。
而这一版把前端从「1959 行单文件」拆成了模块化 ——
老浏览器里那份旧 HTML 是自洽的单文件（自带旧样式和旧脚本），
于是用户看到的是**旧界面、旧阅读器**，而且「翻页方式」这个设置项
在新版才有、旧版根本没有，表现就成了「怎么翻都是上下滚动」。

如果遇到「代码明明改了、界面没变」，强制刷新一次：

- 电脑：`Ctrl + Shift + R`
- 手机：清一次浏览数据；或者换个带参数的地址进（`http://主机:8000/?v=2`），
  浏览器会当成新页面直接请求

之后就不会再有问题了。
